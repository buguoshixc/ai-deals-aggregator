# t12 信息架构收口说明（Stage I）

> 由 pages-builder 在 t12 产出。两件事：**入口怎么挂**、**Global Search 为什么不做**。
> 最终报告请直接引用本文件的结论与实测数字。

## 1. 入口设计（不新增页脚整行）

约束（题面 Stage I + v1.5 密度账）：**不新增页脚整行**；所有资料库入口挂在
**已有的「按厂商 / 分类浏览」那一行**；首页仍突出 AI 优惠，不改首屏密度、卡片数与筛选体验。

| 位置 | 入口 | 说明 |
|---|---|---|
| 页脚「按厂商 / 分类浏览」行 | 厂商优惠 · 分类优惠 · **模型资料** · **套餐与 API 计费** · **历史档案** · 套餐对比 · API 计费对比 · **开放数据** | 8 个入口 + 构建期注入的厂商快捷入口；v3.0 新增的四个（模型资料 / 套餐与计费 / 历史档案 / 开放数据）全部在这一行 |
| 页脚「变化与订阅」行 | 变化雷达 · 订阅这些优惠 | **保持 v1.6 形状不变**（v3.0 没有往这一行加任何东西） |
| 顶栏 | 不变（AI Coding 套餐对比 / API 计费对比） | 资料库不挤进顶栏 |

**页脚路由占位符**：`ROUTE_HREFS` 现在 14 条（新增 `__MODELS_HREF__` / `__PLANSHUB_HREF__` /
`__ARCHIVE_HREF__` / `__DATA_HREF__`），构建期按每个输出深度的前缀逐条解析 + 残留扫描
（166 个输出 × 14 条路由）。

## 3. Global Search：本版本**不做**（可核对理由）

题面 I3 明确不强制。不做的理由不是"没时间"，而是**与本仓既有纪律冲突**：

1. `/plans/coding/` 与 `/plans/api/` 的交互逻辑是**构建期内联**的，而且离线自测 `require`
   的必须是**同一份字节**（`plans-compare.js` 的字节比对断言）。跨 5 类实体（优惠 / 套餐 /
   API 计费 / 模型 / 厂商）的统一搜索，需要在前端再引入一份**跨实体的数据索引**。
2. 那份索引必须有**自己的判据**（什么算命中、怎么排序、缺失怎么办）。而这些判据现在已经各自
   存在于服务端：优惠在 `audience.js`/`changes.js`，套餐在 `plan-schema.js`，API 在
   `api-plan-schema.js`，模型在 `model-registry.js`。前端再写一份 = **第二套判据**，
   正是本仓反复禁止的形态（"判据只有一处"）。
3. 收益侧：现在的站内检索由**浏览器页内查找（Ctrl/⌘+F）**加上分类 / 按需求 / 厂商 / 模型
   四条入口覆盖；要真正超过它，需要的是「跨实体+跨来源」的排序与高亮设计，那是独立一版的
   工作量（tokens 预算、分页、索引体积），不是 v3.0 的收口项。

⇒ 取舍已写进本文件与最终报告；如果下一版本要做，先决条件是**先定索引与判据的唯一出处**。

## 4. verify-site 新增五节（§21–§25）

五节共用一套「页面体检」（`auditLibraryPage()`），每节都查：

- **无 JS 有完整内容**：关掉 JS 打开同一路由，正文 ≥ 该页 `page-kinds` 下限的取整值，
  且关键片段（如「Coding 套餐」「模型名称」「0 条是事实，不是故障」）都要读得到；
- **0 控件**：无 JS 时 `main` 里 `button/select/input/textarea` 一个都不能有
  （`/models/` 的筛选控件由脚本建，有 JS 时才有）；
- **canonical 自指**、**面包屑第一级回站根**（深度由路由段数推导）、
  以及各节特有的「第二级指向枢纽」；
- **ItemList 声明数 == 元素数 == 页面行数**（枢纽页按 `data-child`，其余按 `data-item`）；
- **官方链接逐条**（模型详情 ≥1 条站外官方定价页；厂商页按资料区块接线情况；
  枢纽/索引页按设计 0 条站外链接 —— 断言显式写明这个"0"是设计而非漏掉）；
- **390px / 360px 页面级横向溢出 = 0**；
- **sitemap 成员资格**（从 sitemap.xml 现场解析，不是"文件存在"）；
- **0 外部请求 + 0 JS 错误**（每节自己快照计数，不靠整轮累计）。

实测：`npm run verify` **642 项 0 失败**（t12 之前是 440 项，**新增 202 项**；
机器可读报告 `research/_raw/v3.0-gate/t12-verify5.json`）；
`npm run verify:regress` 648 项 0 失败，**首屏完整可见 9 → 9、页高 4589px → 4665px（+1.7%，容差 15%）**、
0 外部请求、**0 JS 错误**（`metrics.jsErrors = 0`、`metrics.httpNotFound = []`）。

**顺手修掉并加固的两处（都是"看不见的坏法"）**：

1. 我新写的 §24 里把 API 变化日志的地址写成了 `api-history.json`（真实文件名是
   `api-plan-history.json`）⇒ 浏览器在 `/archive/` 上产生一条 `Failed to load resource: 404`。
   每一节的"本节 0 JS 错误"都是绿的（那条错误在快照窗口之外才落地），**只有整轮计数是 1** ——
   回归比对因此报红而现场看不出原因。
2. 为了让这类问题下次**一眼可见**，给 verify-site 加了两处诊断（都进机器可读报告）：
   `metrics.jsErrorSamples`（错误文本**带上当时那一页的 URL**）与
   `metrics.httpNotFound`（本地静态服务记下的 404 路径清单）。修掉上面那处之后两者分别是
   `[]` 与 `[]`。
