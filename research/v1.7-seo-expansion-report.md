## 四、URL / Slug 设计

1. **厂商 slug 的键改成「规范显示名」**。v1.6 之前 `vendor-slugs.json` 键的是采集时的原始字符串，
   于是同一家公司有两种身份（`火山引擎（字节跳动）` vs `火山引擎`、`扣子 Coze（字节跳动）` vs `扣子 Coze`）。
   v1.7 统一到 `vendorOf(deal).name`，并把 `feeds.js` 的分组也切到同一套口径 ——
   做法是**注入** `vendorKeyOf`（不 require RENDER-CORE：那个文件必须保持纯函数、可被自测直接调用）。
2. **slug 值一个都没改**（`baidu-ai-cloud / zhipu / volcengine / coze / github / iflytek / microsoft /
   notion / minimax`）⇒ 老订阅者的 Feed URL 零变化；只有条目集合有微调（火山引擎 12 → 13 条，
   因为它那两条写法合并了）。
3. 分类 slug 在 `scripts/data/category-slugs.json`（人工），分类页文案在 `landing.js` 的
   `CATEGORY_PAGES` 里手写 —— **不从枚举名机械生成**。
4. **改名不改 slug**；必须改时在 `scripts/data/landing-aliases.json` 登记 → 构建自动产出旧路由的
   别名页（`noindex,follow` + 自指 canonical + 指向新页 + 不进 sitemap），别名链最长 1 跳。

## 五、Canonical：自指 + 唯一，以及 3 对近义 URL 的收口

全部 113 页自指 canonical；可索引页之间**不允许共用** canonical（两个检查码分开：`canonical-self`
管「每页说自己」，`canonical-unique` 管「两页说自己是同一个地址」）。

**近义 URL 收口（本轮最大的既有缺陷）**：实测三对页面的**条目集合逐条相同**，其中两对 `<title>` 逐字相同：

| 旧地址（→ noindex 别名） | 目标（被索引的那个） | 实测条数 |
|---|---|---|
| `/need/student-only/` | `/student/` | 12 = 12 |
| `/need/free-api/` | `/free-api/` | 45 = 45 |
| `/need/dev-credits/` | `/developer/` | 67 = 67 |

保留短路由作为被索引入口（它们同时是首页导航与页脚入口），旧地址保留静态页保证外链可用、
页面上如实写明「与目标页是同一批条目，收录以目标页为准」。**没有删除任何 URL。**

## 八、内链结构

```
首页 ──┬─ 按需求入口行（10 条静态 <a>）────────────→ /need/<slug>/
       ├─ 分类页/页脚 ────────────────────────────→ /student/ /developer/ /free-api/
       └─ 页脚「按厂商/分类浏览」+ 前 5 家厂商 ──────→ /vendor/ /category/ /vendor/<slug>/
/vendor/  ──┤ 9 家厂商页
/vendor/<slug>/ ─ 条目 → /deal/<id>/ ，变化块 → /changes/ ，订阅 → /feed/vendor/<slug>.*
/deal/<id>/ ─ 面包屑 → /category/<slug>/ ；正文「这家厂商的其他优惠」→ /vendor/<slug>/
```

四条硬约束（都有断言）：
1. **每个可索引页至少 1 条站内入链**（首页除外）—— `orphan` 检查码；
2. 面包屑每一级**存在的** `item` 必须解析到真实页面（不存在时省略 `item`、保留 `name`）；
3. 页脚那一行的厂商入口由**计划生成**（源码里不留第二份厂商清单）；
4. 新页面的相对前缀由**路由段数推导**（`vendor/zhipu/` ⇒ `../../`），不写死 ——
   写死的症状是「页面打得开、内容全对、所有内链 404」。

## 九、Thin Content 防护

| 防线 | 做法 |
|---|---|
| 生成门槛 | vendor ≥ 2 条、category ≥ 4 条（见 §三），未达标**不生成**、不进 sitemap、首页不出现入口 |
| 空页 | `need` 条数为 0 不生成；**钉住的页面条数为 0 ⇒ 构建红**（不允许空页面上线） |
| 正文下限 | 集合页 `600 + 60×条目数`（沿用 v1.2 口径）、枢纽页 `500 + 60×子页数`；**先剥 `<script>`/`<style>`** 再数 |
| 重复内容 | `duplicate-item-set`：两个可索引集合页的条目集合**逐条相同**即红（`编程开发` 与 `/need/ai-coding/` 正是这种情况 ⇒ 由既有页承担，不建分类页） |
| 数据摘要 | 8 类数字全部现算，且由 `summary-source` **独立重算**对账（「页面写 12、实际列 7」在构建期就红） |
| 变化块 | 0 事件时如实写「记录自 2026-09-30 起，此前没有历史；窗口内该主题没有变化」—— 与「没拿到日志」是两句不同的话 |

| 层 | 位置 | 输入来源 | 结果 |

| 真浏览器 | `verify-site.js` §18 + 详情页/首页 h1 | 真 DOM | 验收 **335 项 0 失败**（v1.6 是 297） |

检查码：`gate-threshold` `gate-pinned-missing` `gate-pinned-empty` `alias-target-exists` `alias-item-set`
`alias-indexable` `slug-shape` `slug-unique` `title-unique` `title-length` `desc-nonempty` `desc-unique`
`canonical-self` `canonical-unique` `h1-count` `robots-policy` `itemlist-arity` `itemlist-members`
`breadcrumb-target-exists` `sitemap-target-exists` `sitemap-policy` `orphan` `internal-link-exists`

**为什么两个执行点都要**：构建期的描述符是构建过程自己记下来的，两份数据同源时，
一个错误的判据会在两边一致地错下去。`verify:seo` 的输入与它完全不同源 —— 这也是
`selftest:seo` 那条「27 个码每条都必须会响」的用意：**一个永远不响的检查码比没有检查码更糟。**

## 十一、Tooth Test（6 条，全部实跑）

每条：注入 → 跑门禁 → 记录逐字红色 → **用文件备份还原**（不是 `git checkout`）→ 复跑确认回到绿。

| # | 注入 | 实测红色（逐字） | 还原后 |
|---|---|---|---|
| 1 | 两个页面共用同一个 canonical | `✗ SEO[canonical-unique] developer/：canonical 与 student/ 相同：https://…/category/api/` + `❌ 构建失败` | exit 0 |
| 2 | sitemap 里出现不存在的 URL | `✗ SEO[sitemap-target-exists] vendor/does-not-exist/：sitemap 里的这条 URL 没有对应的页面` | exit 0 |
| 3 | 厂商页没有效优惠却被生成（门槛被绕过） | `✗ SEO[gate-threshold] vendor/cursor/：vendor 页只有 1 条，低于门槛 2，且未钉住 —— 不该生成` | exit 0 |
| 4 | ItemList 声明 10 项而页面只有 9 行 | `✗ SEO[itemlist-arity] developer/：ItemList 声明 68 项，但 itemListElement 只有 67 项` | exit 0 |
| 5 | 面包屑指向不存在的页面 | `✗ SEO[breadcrumb-target-exists] vendor/baidu-ai-cloud/：面包屑「按厂商浏览」指向不存在的页面：vendor/does-not-exist/` | exit 0 |
| 6 | **人为制造 orphan 落地页**（产物级注入：把指向 `/vendor/notion/` 的每条站内链接改指 `/vendor/`） | `✗ 规则层 27 个检查码全过 —— [orphan] vendor/notion/ 可索引页没有任何站内入链`（由 `npm run verify:seo` 发现，**不是**构建期） | 重建后 exit 0 |

两条测试的**注入方式本身就说明了防线在哪**：
- #3 只关掉「一家厂商」的达标判断 —— 33 家全关会先撞上计划层的另一条守卫（达标却没登记 slug），
  于是验不到 `gate-threshold` 本身；
- #6 **无法在源头造出孤儿**（每个落地页都天然有页脚/枢纽/详情页三处入链），
  所以它验的是「万一产物里出现孤儿，独立验收能不能发现」。

### 一个必须记下来的事故

第一版 Tooth Test 驱动用 `git checkout -- <file>` 还原，而当时的改动**还没提交** ——
「还原」把整份 `build-local.js`（约 300 行改动）清空了。
处置：先把幸存文件提交（`a173933`），再按对话记录逐条重新应用，重建后产物与丢失前**逐字节等价**
（113 页 / 可索引 110 / sitemap 110）；驱动脚本改成**基于当前工作区副本的备份/还原**。
教训：**任何「还原」动作都不能依赖「改动已提交」这个前提。**

## 十五、下一阶段建议

**结论：适合进入 `v2.0-ai-assisted-maintenance`，但有一条前置条件。**

✅ **适合**，三条理由：

1. **门禁已经闭合到「新页上线必须过门槛、重复页与坏链接不可能悄悄发布」**：
   生成门槛 + 钉住表 + 27 个检查码 + 两个不同源执行点 + 6 条 Tooth Test 实证。
2. **索引策略是显式登记的**（可索引 110 / noindex 3 / 资源不进 sitemap），
   不依赖任何人的记忆；改策略必须同时改表、改契约、跑门禁。
3. **页面层不再需要人工扩产**：多一家达标厂商（≥2 条）就会自动出页，且 URL 由人工 slug 表锁死；
   新页面带来的风险（薄页、重复、孤儿、坏链接）全部有检查码。

⚠️ **前置条件（与 v1.6 报告的同一条）**：`deal-history.json` 今天仍是 **0 事件**，
「最近变化」块与变化 Feed 都只能如实显示空态。**AI 辅助维护要判断的第一件事恰恰是「什么变化值得通知人」**，
而这条判据现在没有任何真实样本可校准。建议：

1. 让采集链跑满 3 天（CI 每天两次，约 6 次采集），先拿到真实事件；
2. 用 `npm run report:changes` 复核分栏与高价值判据（**先改 `changes.js` 的判据，不要在页面层加过滤**）；
3. 之后再进 v2.0：那时 AI 的输出（建议、摘要、变更通知）才有可对账的地面真值。

**另外三件可以顺手做的**（按价值排序）：
- 给 `/vendor/<slug>/` 补「该厂商的变化」独立 Feed（事件样本足够后再设计，现在等于再添两份永远空的订阅）；
- 把 `VENDOR_RULES` 里还缺的规范名补齐（例如已合并的 `MiniMax/海螺AI` 之外，
  还有若干 1 条厂商的别名写法），让「同一家公司一个名字」这条更彻底；
- `/status/` 的索引策略做一次真实效果复核（它是唯一一个「保留索引但价值存疑」的页面）。
