## 2. 总体架构决策

1. **分层不合并**（详见 `docs/SCHEMA-v3.0.md` §0）：真值层（三份数据 + 三份日志，字段集**一个都没改**）·
   人工来源层 · 索引层（`models.json` 只回答身份）· 关系层（`model-registry-links.json` 显式映射）·
   归档层（**不落新真值文件**，由 `baseline + events + absence + tombstone` 派生）· 出口层（`/data/index.json`）。
2. **判据只有一处**：模型身份 / 厂商门槛 / 归档状态 / Manifest 数字各一个模块；
   页面、Feed、自测、门禁全部调用它，不许有第二份实现。
3. **URL 策略选方案 A**：继续用 `/vendor/<slug>/`，**不新增 `/provider/`**
   （理由：9 个既有厂商页已达标且 slug 来自显示名，方案 B 会把 9 条 URL 变 noindex 换 0 条新信息）。
4. **数字可重算**：页面计数一律带 `data-*` 标记，构建期**从盘上现读**再对账。
5. **不替用户做判断**：不做推荐 / 排序 / 星级 / 成本计算器 / 跨币种或跨单位换算。

## 18. 已知限制（如实记录，不粉饰）

1. **`/archive/` 交付日必然为空**：三份日志的 `ended` / `restored` 事件都是 0 条
   （deal 0 事件；plan 14 条全是 `created`；api 6 条全是 `created`）。
   ended/restored 两条分支**只由合成夹具驱动**（`selftest:archive` 61 项），
   **不得为了填满页面而补造事件**。第一次真正有资料下线时它会自动生效。
2. **数据许可证未定**：仓库没有 `LICENSE` / `COPYING` 文件 ⇒ `/docs/data/` 与报告都写
   「需项目所有者决定」，**本仓不擅自决定**。
3. **未映射的套餐模型串 11 条**：区间 / 池 / 资源包 / 家族名 / 版本歧义 —— 只进候选与覆盖报告，不写生产映射。
4. **`credits` 与跨单位换算刻意不做**：`credits` 不折算成 token；`per_1M_tokens` 与 `per_1K_tokens` 不互相换算。
5. **题面 §16 的 7 个脚本名与实际 `package.json` 不一致**（§1 已逐条列出）。
6. **厂商页 19 家里的 DeepSeek 是 0 条优惠**：它靠「非优惠资料」（2 条 API 记录 + 3 个模型）达标，
   标题按设计是「DeepSeek 的 AI 资料」；正文靠资料区块满足 ≥600 字下限。
7. **四家 provider（trae / qoder / codebuddy / qoder-intl）没有 `/vendor/` 路由**：
   它们在 A 空间没有厂商名（`vendorKey=null`），资料走 `/plans/coding/` 与 `/plans/` 枢纽。

## 题面最后五问（直接回答）

**1. v3.0 是否真正完成了「资料库化」，而不是只新增几个页面？**
是，而且判据不是「页面数」而是**三条可验证的性质**：
① **同一件事只有一个判据**（模型身份 / 厂商门槛 / 归档状态 / Manifest 数字各一个模块，页面 / Feed / 自测 / 门禁全部调用它）；
② **每个数字都能从盘上重算**（页面计数带 `data-*` 标记，构建期现读对账；真浏览器再独立复算一遍）；
③ **跨实体的关系是显式的**（63 条模型映射 + 5 条优惠↔套餐关系，全是人工写、机器校验，
   没有任何相似度或 LLM 猜测路径）。页面是这三条的外显，不是反过来。

**2. 当前最大的瓶颈已经变成代码、数据覆盖还是人工维护？**
**人工维护**。代码与门禁已经不缺：39 步门禁、36 条 CI 断言、20 条牙、651 项真浏览器验收（回归比对 657 项），
新增一类页面的边际成本是「一个模块 + 一个自测 + 一条登记」，很便宜。
瓶颈在人工来源层：44 条 registry 模型对应 63 条映射是**一条条人写**的，
11 条套餐模型串因为「区间 / 池 / 资源包 / 家族名」不可机械判定而**只能留空**。
数据的**规模**不是问题，**判定**才是。

**3. 哪些重要 Provider 仍缺数据，以及为什么？**
① **四家只有 Coding 套餐、没有 A 空间厂商名的**（trae / qoder / codebuddy / qoder-intl）——
   它们不是「缺数据」，而是**身份上不属于 `/vendor/` 这个空间**，资料走 `/plans/coding/`；
② **只有 1 条优惠、也没非优惠资料的 12 家**（360 智脑 / 百川智能 / 阶跃星辰 / 商汤 / AWS / Canva /
   ElevenLabs / Figma / Perplexity / Replit / Runway / Zapier）—— 未过厂商页门槛，如实跳过并逐条留痕；
③ **有 API 计费但没有免费额度的平台**：`freeTier` 只在 google 与 zhipu 上有（官方口径就是「没有」或「未公布」），
   如实写「—」与「尚未确认」，不编。

**4. Model Registry 还有多少未映射项？**
**API 侧 0 条**（`unmappedModelKeys = 0`）；**套餐侧 11 条**（`supportedModels` 是自由文本，无模型键），
逐条理由已列在覆盖报告里。44/44 registry 模型都被至少一个当前或历史实体引用。

**5. 下一版本最值得投入的方向是什么？**
**把「人工判定」这件事的产能提上来，而不是再扩页面**：
① 给 `/archive/` 等的真实样本做一次线上对照（等第一件真实下线）；
② 把 11 条未映射逐条判定（人工）；
③ 把「本站不做单位/币种换算」「credits 不是 token」这类**读者最常误解的口径**提到更显眼的位置；
④ 若要继续扩数据，优先补**每个平台的免费额度官方口径**（现在大面积是「未公布」），
因为它是读者最关心、也最容易被第三方聚合站写错的一项。
