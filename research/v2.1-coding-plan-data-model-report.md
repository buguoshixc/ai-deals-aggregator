### 0.3 Deals 与 Plans 应该如何隔离

- **文件**：`deals.json` ↔ `plans.json`，两套 `schemaVersion`（2 / 1）、两套数组名（`deals` / `plans`）。
- **语义**：Deals = 现在有什么优惠；Plans = 长期在售的套餐是什么。**不互相注入字段**。
- **判据**：`validate.js` 里 plans 走独立的 `checkPlansFile()`；`check-reproducible.js`（deals 五判据）
  **没有**扩展到 plans —— plans 有自己的 `check-plans-reproducible.js`，两者红的含义不同。
- **身份**：deals 的 `vendor` 是采集来的原始串、渲染期归一；plans 的 `provider` 必须是登记过的规范 key。
  两者只在 slug 一致性断言处相遇。
- **发布面**：`plans.json` **不进 dist**、`build-local.js` 不读它 —— 本阶段零页面影响（§实际测试结果 有实证）。

### 0.4 哪些字段存在语义冲突，以及怎么处置

| # | 冲突 | 处置 |
|---|---|---|
| C1 | `period` 在 `billing` 与 `quota` 下都出现，含义不同 | 两个都保留并写明（计费周期 vs 额度刷新周期）；派生指标要求两者相等才计算 |
| C2 | deals 的 `priceLine` 是自由文本 | Plans 不设该字段，价格只进数值字段 |
| C3 | deals 的 `pricingModel`（free/paid/…） | Plans 不复用该字段名（同名不同义），免费档用 `regularPrice = 0` |
| C4 | deals 的 `source` 是**采集器名** | Plans 的 `source` 是**页面类型**，独立登记表，**不**登记进 `provenance.SOURCE_TYPES` |
| C5 | deals 的 `provenance` 可信度块 | Plans 只复用 `evidence`，不引入 `credibility/contrib/fields`（那是 merge 仲裁的产物） |
| C6 | deals 的 `availability.chinaUsable` | Plans 只存 `region`，"地区限制"交给 `restrictions.region_restriction`，避免两处表达同一件事 |
| C7 | `vendor` vs `provider` | 两套身份空间；同一公司允许两个 provider（字节的火山引擎 / Trae），但必须逐条登记 |
| C8 | `evidence.field` 白名单是 deals 的 10 个字段 | `provenance` 增加 `opts.fields`（**默认值不变**），Plans 传自己的白名单 |
| C9 | 题面示例键名 `nominalCNYPer100MTokens` 把币种写进键 | 改为币种中立的 `derivedMetrics.nominalUnitPrice`（内含 `currency`）。理由：题面 §九 禁止在真值层改写成人民币。**这是对题面示例的有意偏差** |
| C10 | `isGarbage()` 对 <3 字符一律判垃圾 | Plans 的 `planName` / 模型名**不用**它（会误杀 `o3`、`Go`），改用"非空 + 长度上限 + 规范形态" |

## 数据契约

```
scripts/data/curated_plans.json  ──(makePlan：归一 + 算 id + 算 derivedMetrics)──▶  plans.json
        （人写事实；不写 id、不写 derivedMetrics）
```

- 人工来源层是**事实的唯一权威**；`plans.json` 是**派生产物**（可重建、可逐字节复核）。
- 每条记录三个时间：`firstSeen` / `lastSeen` / `verifiedAt`，全部人工写、非未来。
- 顶层 `updatedAt` = **全部 `lastSeen` 的最大值**（不读墙上时钟）—— 没有采集器就没有理由盖今天的章。

## Schema

```json
{ "schemaVersion": 1, "updatedAt": "2026-10-01T00:00:00+08:00", "count": 9, "plans": [] }
```

记录字段与顺序（顺序即序列化序）：

```
id · kind · provider · planName · officialUrl · source · sourceUrl · region
billing · quota · supportedModels · restrictions
firstSeen · lastSeen · verified · verifiedAt · evidence · derivedMetrics
```

| 字段 | 说明 |
|---|---|
| `id` | 12 位小写 hex，**派生**，不得手写（校验器重新推导后逐字段比对） |
| `kind` | `"coding"`；为 Phase 2.5 的 Base/Coding/Api 判别位预留 |
| `provider` | `providers.json` 里的规范 **key**（未登记硬红） |
| `planName` | 非空、≤80 字、NFKC 规范形态（**超长报错，不截断**） |
| `officialUrl` / `sourceUrl` | http(s)、无追踪参数、非聚合站 |
| `source` | `Official-Pricing` / `Official-Docs` / `Official-Announcement`（登记制） |
| `region` | `cn` / `global`（复用 `schema.REGIONS`） |
| `billing` / `quota` / `supportedModels` / `restrictions` | 见下四节 |
| `firstSeen` / `lastSeen` / `verifiedAt` | `YYYY-MM-DD`；非未来；`firstSeen ≤ lastSeen`；`verifiedAt ≤ lastSeen` |
| `verified` | v2.1 **必须为 true**（每条都是人工对照官方页核过的） |
| `evidence` | **≥1 条**（与 deals 的"可选"不同）；复用引文层：≤3 条 × ≤200 字、官方 host、超长拒收 |
| `derivedMetrics` | 永远存在；不可比较时值为 `null` |

**严格归一**：与 `makeDeal`（能洗就洗）不同，`makePlan` 对规范形态是严格的 —— 超长、多余空白、
URL 带追踪参数、枚举拼错、`planName` 非规范形态一律**报错**而不是悄悄改正（唯一例外是日期写法）。
理由：被静默改写的输入与"本来就没写"在产物里长得一模一样。

**键序确定性**：`plans` 按 `kind|provider|planName|period` 升序；`supportedModels` 按
`(role, name)`、`restrictions` 按 kind 声明序、`evidence` 按字段序 + 引文 + 日期排序 ——
**打乱输入顺序产出必须逐字节相同**（有断言）。

## Price Model

```json
"billing": { "period": "monthly", "currency": "CNY",
             "regularPrice": 99, "promoPrice": 69, "promoNote": "首月优惠低至 ¥69/月", "note": null }
```

- `period` ∈ `monthly / yearly / one_time / usage_based / other`（必填）。
- `currency` ∈ `CNY / USD / HKD / EUR / JPY / GBP / SGD`；**当且仅当两个价格都是 null 时允许 null**。
- `regularPrice` = `null`（**原价未知**）或 `[0, MAX_PRICE]`；`0` 是"确实免费"的合法值。
- `promoPrice` = `null` 或 `(0, MAX_PRICE]`。**活动价不替代原价**。
- **唯一的价格关系判据**：两个价格都非 null 时必须 `regularPrice > promoPrice`。
  这一条同时挡住「原价未知却填 0」与「活动价高于原价」。
- 「只有活动价、原价确实不知道」是**合法**的（`regularPrice: null` + `promoPrice: 49`）。
- **没有任何汇率**：跨币种不比较，需要人民币展示只能建派生层（本阶段不做）。

真实数据：**9 条里 2 条有活动价**（Trae 会员 Pro `99 → 69`、CodeBuddy 标准版 `99 → 70`），
**1 条原价留空**（智谱 GLM Coding Plan Lite —— 官方文档页确实没公布当前档位价格，
页面上只有积分额度与抵扣规则）。免费档用 `regularPrice: 0` 表达（Trae 免费 Free）。

## Quota Model

```json
"quota": { "type": "credits", "amount": 2000, "period": "rolling",
           "description": "每 5 小时 2,000 积分 + 每周 10,000 积分双窗口上限…",
           "conversionDependsOnModel": true }
```

| `type` | `amount` | `description` |
|---|---|---|
| `tokens` / `credits` / `requests` / `messages` / `compute_units` | 必填 > 0 | 可选（credits 的 `conversionDependsOnModel` 必填） |
| `rate_limited` / `unlimited_fair_use` | **必须为 null** | 必填 |
| `other` | 可选 | 必填 |

- `conversionDependsOnModel` **只允许出现在 `credits` / `other`** ⇒ `tokens` 上写 `true` 判红
  （题面 §五：额度随模型倍率变化时必须表达为 credits，不得伪装成固定 Token）。
- **没有**任何把 requests / credits / fair use 折算成 Token 的真值字段。

真实数据的额度类型分布：**credits 6 · other 2 · rate_limited 1 · tokens 0**。
这直接决定了派生指标一家都算不出来（见下节）。

## Supported Models

```json
"supportedModels": [ { "name": "GLM-5.3", "role": "included", "note": null } ]
```

`role` ∈ `included`（可直接使用，缺省）/ `limited` / `pool`（动态模型池）/ `family`（模型族）；
名称归一化去重；**空数组非法**（缺席写 `null`）；排序后与输入顺序无关；**不建模型注册表**
（仓库里没有可复用的 registry，本阶段也不新建 —— 模型名以厂商原文为准）。

真实数据：3 条带 `supportedModels`（Trae 会员 Pro 列了 5 个折扣模型、智谱列了 GLM-5.3 /
GLM-5.3-Flash、MiniMax 列了 M3 / M2.7 / 图像语音资源并注明共享额度）；其余 6 条官方页没有
给出模型清单，写 `null` 而不是编一个。

## Restrictions

```json
"restrictions": [
  { "kind": "rolling_window", "value": "5 小时动态刷新 + 7 天周周期", "note": "额度耗尽后需等待下一个 5 小时周期恢复" },
  { "kind": "new_user_only", "value": "unknown", "note": "官方页面未说明领取资格" }
]
```

`kind` 与值类型：`concurrency`/`per_day_cap` → 正数；`rate_limit`/`rolling_window`/`output_limit`/
`region_restriction` → 非空文本；`fair_use`/`account_required`/`invite_only`/`new_user_only` → 三态。

**三态与 deals 完全一致**：缺席 = 没写；`false` = 来源明说"不是"；`"unknown"` = **查过、来源没说明**
（必须带 note 说明依据）。`0` / `1` / `"true"` 一律拒绝 —— **为未知值填 false 是硬错误**。

真实数据：4 条带 `restrictions`（Trae 免费/Pro 的并发 2 / 10、智谱的双窗口 + 公平使用策略、
Kimi 的 Kimi Code 独立 5 小时/每周上限）。

## Derived Metrics

```json
"derivedMetrics": { "nominalUnitPrice": {
  "price": 1, "currency": "CNY", "per": 100000000, "basis": "monthly", "priceField": "regularPrice" } }
```

**五个条件同时成立才产出**（否则一律 `null`）：`quota.type === 'tokens'` 且 `amount > 0`；
`quota.period` 非 null、等于 `billing.period` 且该周期 ∈ `{monthly, yearly}`；币种在白名单内；
当前使用价格（`promoPrice ?? regularPrice`）明确且 > 0；`conversionDependsOnModel !== true`。
计算 `round6(当前价 / amount × 1e8)`，并记录用的是原价还是活动价（`priceField`）。

**不做汇率换算，也不做 12 个月的隐含换算**（年付以年为口径，`basis` 写明）。
口径声明是常量 `PLAN_WORDING.nominalUnitPriceNote`，**不写进数据**。

### 真实数据的结果：9 条全部为 `null` —— 这是结论，不是缺省

| 平台 | 额度类型 | 为什么算不出单价 |
|---|---|---|
| Trae 免费 / 会员 Pro | credits | 积分按模型折扣折算（Seed-2.1 2.5 折、GLM/Deepseek 5 折），随模型变 |
| 智谱 GLM Coding Plan Lite | credits | 积分按 `(输入×系数 + 缓存命中×系数 + 输出×系数)/10000` 折算，系数随模型变 |
| Qoder CN 个人专业版 | credits | 积分跨产品共享、随模型倍率变化 |
| 腾讯 CodeBuddy 标准版 | credits | 积分与 WorkBuddy 共享，随模型倍率变化 |
| 月之暗面 Moderato | other | 共用积分池、未公布固定数值 |
| Cursor Pro | other | 用量池、未公布固定数值 |
| MiniMax Token Plan Plus | rate_limited | 5 小时 + 周窗口，没有固定额度 |
| GitHub Copilot Pro | credits | GitHub AI Credits（1,500/月），随模型倍率变化 |

**没有任何一家厂商在官方页面上给出固定的 Token 额度。** 智谱文档页另有一张
"可用额度参考（亿 Tokens/周）"表，但它**随缓存命中率变化**，不是一个固定数值 ——
按契约属于"折算随模型倍率变化"，只能记 `credits`，不能记固定 tokens。

所以本阶段最重要的那条纪律（题面 §八"如果不可比较，对应值必须为 null，不要强行算"）
在真实数据上被**执行了 9 次**，而不是靠夹具演示。可计算路径由夹具覆盖：
60 元 / 60 亿 tokens = **1 元每亿**；活动价优先（`priceField: 'promoPrice'`，0.5 元每亿）；
年付以年为口径（10 元每亿）。

## Provider Normalization

`scripts/data/providers.json` 以 **provider key** 为键，每条含 `name`（显示名）/ `slug` /
`aliases`（**已归一形态**，精确匹配） / `logo`。

- **`provider` 存 key 不存显示名** ⇒ 显示名改动不会改 id。
- **未登记一律硬红**并给出建议 key（`suggestProviderSlug`）—— 逼人显式登记，而不是静默分裂身份。
- **精确匹配而非子串/正则**：子串匹配在本仓库有实测教训（`/krea/i` 会命中 "Kreado AI"）。
- **与 deals 侧交叉一致性**：provider 的 `name` 若也是 `vendor-slugs.json` 的键，两边 slug 必须
  逐字相同。真实数据里这条断言在 **智谱AI / MiniMax（稀宇科技） / GitHub** 三家上生效。
- **同一公司允许两个 provider** 并逐条登记：字节跳动的「火山引擎」（deals）与 `trae`（plans）、
  腾讯云的「腾讯云」（deals）与 `腾讯 CodeBuddy`（plans）。
- `SLUG_RE` 与 `landing.js` 的那一份由 selftest 逐字比对，不许分家。

真实数据：8 个 provider（zhipu / trae / qoder / codebuddy / moonshot / minimax / github / cursor）。

## ID Strategy

```
id = sha1(`${kind}|${provider}|${planNameKey}|${billing.period}`).slice(0, 12)
```

- **不进 basis**：价格、额度、日期、URL、证据 ⇒ **改价 / 改额度 / 换官方页 / 改备注都不换 id**。
- **进 basis**：`kind`（为 Phase 2.5 预留）· `provider`（规范 key）· `planNameKey` · `billing.period`。
- 数据集级**双重保险**：`id` 唯一 **且** `identityKey = kind|provider|planNameKey|period` 唯一 ——
  同平台的同一套餐不可能有两条身份，手写 id 也拦得住。
- 12 位小写 hex，与 deals 的 id 同长，复用同一套 `/^[0-9a-f]{12}$/` 纪律。

## Source Strategy

- 每条 plan 必须能追溯 `officialUrl` + `source` + `sourceUrl` + `lastSeen` + `verifiedAt` + ≥1 条引文。
- `officialUrl` 与引文出处都不得是聚合站（`layer3labs.io` / `futuretools.io` / `futurepedia.io` /
  `aitools.fyi`）。
- **第三方套餐对比站只能用于发现候选**：只有第三方证据的候选**不进 `plans.json`**
  （`source` 登记表里也没有第三方值）。本阶段第三方的信息只用于"知道该去看哪一家的官方页"，
  **最终没有一条事实来自第三方**。
- 引文层复用 `provenance.js`：≤3 条 / 每条 ≤200 字（超长拒收不截断）、`capturedAt` 非未来、确定性排序。
- 引文是**有界抽样不是全文覆盖**：每条最多 3 条，优先保证价格与额度口径的那几句原话。

## Validator

**判据只有两处实现**：`scripts/lib/plan-schema.js`（`makePlan` / `validatePlan` / `validatePlansStore`）
与 `scripts/lib/providers.js`（provider 表 + slug 一致性）。`validate.js` 只负责把它们跑起来、
把结论并进同一份 error/warn 账。

**校验的做法是「把归一器再跑一遍」**（与 v1.3 的 `validateEvidence()` 同一手法）：
`validatePlan()` 用 `makePlan(plan, { fromRecord: true })` 把盘上那条记录重新归一一次，再逐字段比对。
好处是"什么算合法"只有一份实现：手改 `id`、手算 `derivedMetrics`、枚举拼错、文本多了个空格，
全部表现为"与归一结果不一致"，而且错误信息能指名道姓到字段。

题面 §十四 要求的每一项都有对应判据（逐条对照）：

| 题面要求 | 实现 |
|---|---|
| id 唯一 | 数据集级 `id` 唯一 + `identityKey` 唯一（双重） |
| provider 非空 | 必须非空且**已登记**（未登记红并给建议 key） |
| planName 非空 | 非空 + ≤80 字 + 规范形态 |
| URL 合法 | http(s) + 无追踪参数 + 非聚合站（`officialUrl` 与 `sourceUrl` 各自） |
| currency 合法 | 币种白名单 + "有金额才有币种" |
| price >= 0 | `regularPrice ≥ 0`、`promoPrice > 0`、都 ≤ `MAX_PRICE` |
| promoPrice 合法 | `promoPrice > 0`；两个都非 null 时 `regularPrice > promoPrice` |
| quota.type 枚举合法 | 8 值枚举 + 按类型判 amount / description / conversionDependsOnModel |
| tokens amount > 0 | 量纲型必须给正数 amount |
| derivedMetrics 只在允许场景出现 | **逐字节等于重新推导的结果** |
| 不可比较 quota 不得生成 Token 单价 | 同上（5 个条件缺一即 null，写非 null 就红） |
| firstSeen / lastSeen 合法 | 格式 + 非未来 + 先后关系 + `verifiedAt ≤ lastSeen` |
| unknown 与 false 不混淆 | 三态字面量白名单（`0`/`1`/`"true"` 全拒）+ `"unknown"` 必须带 note |

**入口对账**：人工来源层里"写了却没生效"的东西（`id`/`derivedMetrics` 被写、引文被拒收）
由 `loadCuratedPlans()` 逐条报出，`validate.js` 把它们翻成**硬错误** ——
与 `checkCurated()` 同一条理由：校验器看得到的是归一**之后**的世界。

## 已知限制

1. **`billing.period` 进 id basis** ⇒ 同一套餐从月付改年付会被视作两个身份。这是刻意的取舍
   （月付/年付价格不可直接比较，本就该是两条记录），但 Phase 2.3 做变化追踪时必须**显式决策**
   （按 `ended + created` 记，或另立关系），不能让它变成两件没人注意到的孤立记录。
2. **没有采集器**：`plans.json` 目前完全靠人工维护 + 离线重建。`lastSeen` 只在人回访官方页时更新；
   套餐调价、额度变更都不会自动进来。这是 Phase 2.1 的刻意边界（题面没要求采集），
   代价是**维护成本落在人身上** —— 现阶段 9 条、每条 3 条引文，是可接受的。
3. **没有汇率**：跨币种不可比较（USD 与 CNY 的套餐在派生指标层永远不会出现在同一个排序里）。
4. **引文是有界抽样**（每条 ≤3 条）：不能保证覆盖套餐页上的每一句话。
5. **模型名没有归一化**：同一模型在不同厂商页面上的写法（`GLM 5.2 / 5.3` vs `GLM-5.3`）不会自动合并。
   本阶段刻意不建模型注册表；Phase 2.5 若要做 API 价格对比，必须先把这件事单独设计（题面 §六）。
6. **`plans.json` 不进 dist、没有页面**：读者现在还看不到这些数据（Phase 2.2 才发布）。
7. **官方页会变**：本次抓取的文本可能已经与今天不同；`verifiedAt` 记录的是"我们上次核对的日期"，
   不是"官方承诺不变"。
8. **措辞红线尚未自动化**：题面 §四 禁的"性价比 / 最划算 / TOP 1"目前只是**产品规则**，
   仓库里没有脚本检查它们（`provenance.STAMP_PATTERNS` 只管"已核验/永久有效"那一类）。
   Phase 2.2 引入页面文案时应当把它们补成可失败的断言。

### 一处设计判断的纠正（以本节为准）

## 页面契约

11 列：平台 · 套餐 · 正常价格 · 当前活动价 · 计费周期 · 可用模型 · 额度类型 · 原始额度 ·
名义 Token 单价 · 最近更新 · 备注。每行 `<tr data-item="<plan id>">`；
JSON-LD 三段（`CollectionPage` + `BreadcrumbList` + `ItemList`）；
`ItemList` 每条指向**该套餐的官方定价页**（与首页同一口径：主链接给到厂商官方页）——
因此 `itemlist-members` 在构建期与独立验收里都显式关掉，而**声明数 == 元素数 == 页面行数**照常查；
可索引、进 sitemap（priority `0.9`，与分类页同级）、声明两个根 Feed、正文下限 1140 字（实测 2971）。

**未知的三种写法**（H4b 在页面上的落点）：`未标注`（文本缺失）· `—`（数值缺失或**不可比较**）·
`未确认`（三态）。而且**「原价未知」与「确实免费」是成对断言**的：
`regularPrice === null` ⇒ 必须显示 `未标注`；`regularPrice === 0` ⇒ 必须显示含 `0` 的数字。
只查一半（"未知不许是 0"）会在另一个方向漏掉 —— 把免费档也写成"未标注"，读者就再也看不到它。

**渲染层的 fail-closed**：`planRowOf()` 只在 `quota.type === 'tokens'` 时才显示名义 Token 单价。
数据层已经保证过这件事，所以正常数据上这行没有作用；它挡的是"数据被绕过"的那一种 ——
把 requests / 限速 / 用量池显示成一个 Token 单价，是这一页最坏的错（读者会拿它去比"谁更便宜"）。

## 这一段新抓到的两个真问题（都是断言抓的，不是人看出来的）

1. **面包屑回站根写成了 `../`**。`/plans/coding/` 是两层路由，`../` 会解析到 `/plans/` ——
   一个不存在的地址。构建期 SEO 的 `internal-link-exists` 当场报
   「站内链接指向不存在的目标：plans」。改成由路由深度推导的前缀，
   并补了两条断言（离线 + 真浏览器各一条）把它钉住。
   > 这正是 `/status/` 那一页留下的教训的第二次命中：**页面上看起来完全正常，只有点下去才发现问题。**
2. **页面诚实性断言的第一版会在正常数据上失败**。判据写成「整行里有没有 `0`」，

   既没有歧义，也比正则强 —— 它同时钉住了「未知那一格显示的到底是什么」。

（同一轮里还有第三个：Trae 免费档 `regularPrice: 0` 渲染成 `¥0`，被"未知不许是 0"那条
