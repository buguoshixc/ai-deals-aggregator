## 三、关键决策与依据

| 决策 | 依据 |
|---|---|
| **基准日 = 数据时间**（`deals.json` 的 `updatedAt` 日期），不是构建时刻 | 与卡片上的「数据更新」同一口径（页面上不会出现「基准日比数据还新」）；同一天两次构建产物逐字节相同 |
| **不注入 `dist/deals.json`** | 条带与页面都是静态的，浏览器不需要多拿一份；`dist/deals.json` 的顶层键因此与源文件保持一致（实测：四个键逐个相同） |
| 五栏**互不重叠、全覆盖**：过去 6 天内的 `created` 归入「最近 7 天变化」（标「首次收录」） | 否则「3 天前新增」的条目会哪儿都不显示；今天是哪天由 `at === 基准日` 决定 |
| 「即将结束」是**状态量**（`expiresAt` 现算），不参与事件覆盖计数 | 它不对应日志里的任何事件 —— 这条是演练抓出来的（见 §五） |
| `ended` 加可选墓碑 `label` | `title`/`vendor` 是身份字段、刻意不被跟踪；记录离开数据集后，雷达上就只剩一个 12 位 id。墓碑是**快照**，不进链校验、不参与重放，缺席合法 |
| 首页条带**与「跳到档位」共用一行** | 实测：网格起点 227px、卡片 192px、行距 12px、档间分带标题 26px ⇒ 第三行底边 **899px**，距视口底边只剩 **1px**。任何独立成行的条带都会把首屏完整可见从 9 张压到 6 张 |
| `.hubline .jump { flex: 0 0 auto }`（跳到档位不许收缩） | 第一版让它可收缩，四个 chip 于是内部折行、整行 +28px、网格起点 261px、首屏 **6 张**（演练实测）；改后回到 227px / **9 张** |

## 五、真实数据演练（非空路径只能这样证明）

**为什么必须演练**：v1.5 交付当天 `scripts/data/deal-history.json` 是 **0 条事件**（v1.4 的起算日
就是当天），`deals.json` 里 **0/80 条**写了 `expiresAt`。空态能测，**非空路径测不到**。

**做法**：临时在真实数据上造六类变化，全部是 v1.4 契约允许、且能被 `check:history` 重放验证的：

| 造的事 | 期望落点 | 实测 |
|---|---|---|
| A `discountInfo` 真变化 | `benefit_changed` → 高价值 | ✅ 条带第 2 项 |
| B `discountInfo` 只加尾随空格 | 文案微调 → 折叠块、不上首页 | ✅ `other.cosmetic=1`，首页无它 |
| C `category` 换成枚举里另一个值 | 元信息 → 折叠块 | ✅ `other.metadata=1` |
| D 标题加后缀 ⇒ id 变了 | 旧 id：`ended`（带墓碑）+ 新 id：`created` | ✅ 「已结束」1 条（无链接、标题取自快照）+「今日新增」1 条 |
| E `ended`(前天) + `restored`(今天) | 生命周期成对 | ✅ 两栏各 1 条 |
| F 补 `expiresAt = 基准日+4` | `expiry_changed` + 即将结束 | ✅ 「剩 4 天」 |

**结果**：`check:history` 绿；`build` 自检全过（覆盖不变量成立、条带 3 项、`/changes/`
五栏分别 1/2/1/2/1 条、其他变化 2 条）；`verify` **281 项 0 失败**（含 8 条内链 HTTP 200 +
详情页含「变更记录」块、首屏仍 **9** 张、390px 条带 28px 零溢出）。
随后 `restore-from-git.js` **逐字节还原**两个文件（SHA256 与演练前一致）并复跑全套门禁。

**演练抓出的三个真问题**（都不是读代码看出来的）：

1. `radar.WINDOWS.soonDays` 拼错（应为 `radar.windows`）—— 只在「有截止日期但都不在窗口内」
   这条分支上炸，空态下永远不会触发。
2. **覆盖不变量把状态量算成了事件**：`endingSoon` 由 `expiresAt` 现算、不对应日志事件，
   把它加进「覆盖数」会让等式恒差几条（空态下恒等于 0，看不出来）。
3. **页面折叠块里的链接没进链接集合对账**：`/changes/` 的「其他变化」行**也会**链到详情页，
   只数五个分栏会误报「多了 2 条不在雷达里的链接」。

> 另外，密度那条（独立成行 ⇒ 首屏 6 张 / 共用一行 ⇒ 9 张）也是演练态量的 —— 空态条带只有
> 18px，看不出 `.jump` 被压缩后 chip 折行的问题。

## 八、诚实性与边界

1. **交付当天雷达是空的**，并且页面**不说**「没有变化」以外的话：空态明说「当前没有观测到变化
   （记录自 2026-09-30 起）」，`/changes/` 逐栏给出具体原因。**没有补造任何历史事件。**
2. **不补 `created`**：存量 134 条在 v1.4 之前没有历史，v1.5 一条都不补（与 v1.4 同一条红线）。
   因此「今日新增」在起算日之前永远是 0 —— 这是事实，不是故障。
3. **「已结束」不说成「厂商下架 / 优惠失效」**：每行写的是精确原因（来源不再列出 / 过期下架 /
   超出收录上限 / 判定为无效数据后退役），块尾是 v1.4 的固定免责句（原文复用，不新造）。
4. **没有标题快照就说没有**：渲染成「已移除的记录（无标题快照）」，不拿 id 之外的任何东西去凑。
5. **工具条目有变化但不上链接**：`type === 'tool'` 没有静态详情页，构建自检会拦死链。
6. **覆盖率如实上报**：「即将结束」为空时区分「一条都没写绝对截止日期」（附 `0/80` 实测）
   与「有 N 条写了但都不在 7 天内」。
7. **`/changes/` 始终生成**：即使五栏全空也出页 —— 路由凭空消失比一页说明更糟；
   而「今天有没有变化」本身就是这一页要回答的问题。

## 九、遗留与技术债

1. **首页条带在窄屏占一行**（约 24–28px）。v1.2 已经把窄屏首屏卡片压到 0–1 张，这是既有取舍的延续；
   桌面端**没有**额外占行（与「跳到档位」共用）。
2. **条带最多 3 项、每栏最多 30 行**：超出只显示「另有 N 条未显示」。单条记录的完整历史仍在
   它自己的「变更记录」里（受 v1.4 的 `RENDER_LIMIT = 20` 约束，更早的只显示条数）。
3. **`ended` 的墓碑标签只对新事件生效**：交付时 0 条事件，因此没有历史遗留问题；若将来出现
   手工写入的 `ended`（不带 label），页面会如实说「无标题快照」。
4. **「最近 7 天变化」不显示超过 7 天的 `created`**：边界写在契约里（第 7 天起不再出现）。
5. **雷达没有自己的订阅源**：`/changes/` 声明双 feed，但 feed 里仍是「内容更新」（80 条优惠），
   不含变更流。要做「变化订阅」是独立议题。
6. **`CHANGES_WORDING` 是前端受控副本**（RENDER-CORE 不能 `require`）：由构建自检逐项比对，
   与 v1.4 的 `HISTORY_WORDING` 同一套机制。

## 十、是否适合进入 v1.6

**证据侧已经就位，但有一个前提必须先解决。**

支持继续做的时间维度能力：

- **事件管道是活的**：v1.4 的 `check:history` 强迫「日志与当前状态一致」，v1.5 的产物自检强迫
  「条带 ↔ 页面 ↔ 日志」三方对账。加一个新的视图（比如按厂商聚合的变化率、或按分类的变化看板）
  只需要再写一个「取视图」的纯函数 —— 存储、链路、窗口边界都不必再动。
- **窗口与上限是可配的**：`WINDOWS` / `LIMITS` 已经参数化，`buildRadar` 收 `limits` 覆盖
  （自测正是这么用的）。

前提（v1.5 不代劳）：

1. **先有真实事件再谈聚合粒度**。交付当天 0 条事件，所以「按厂商聚合」「按天聚合」这类设计
   仍然是在猜一个没有样本的分布 —— 与 v1.4 报告第十节的结论相同，本轮只是把**取视图的地基**
   铺好了。建议至少观察一个采集周期（2–3 天，CI 每天两次）。
2. **首页那一行的预算已经花光**（余量 1px）。任何再往首页加东西的提议，都必须先量
   「第三行底边还剩几 px」，或者先决定砍掉哪一行。
