## 六、报告素材（供 t13 写最终报告 §8 引用）

### 6.1 同公司两 provider 的登记决定：Qoder CN 与 Qoder International

- **事实**：`docs.qoder.com`（国际站）与 `qoder.com` CN 站是两套独立定价 —— 国际站 Pro $20 / Pro+ $60 / Ultra $200（USD），CN 站个人专业版 ¥59（CNY）。
- **决定**：新建 provider `qoder-intl`（显示名「Qoder International」、slug `qoder-intl`、`vendorKey: null`），**不与 `qoder`（显示名「Qoder CN」）并表**。
- **理由**：并表会让同一张表里出现两套货币与两个站点的人群/可购性，正是本仓最忌的展示错误；本仓既有先例允许同一家公司有两个 provider（字节的火山引擎与 Trae），但必须逐条登记。
- **三条纪律**：① 显示名不取「Qoder」，避免同一家公司两个相似显示名；② `vendorKey` 必须为 `null`（A 空间没有对应厂商名，不得为此新编）；③ 既有 `qoder` 记录（provider 与 id）一个字都不改。
- **想过 `validateSlugAgreement` 这一层**：该断言比的是**显示名** —— 「Qoder International」不在 `vendor-slugs.json` 里，因此不会与 `qoder` 的 slug 产生约束；新增 provider 的别名刻意都不含裸串 `qoder`，不占用既有 provider 的别名。

### 6.2 架构决定：provider-only 平台不建 `/vendor/` 页

- **背景（t3 实测）**：以下 5 家 provider **没有 deals**，只有套餐 / API 计费资料：
  `trae`（plans 2 条）、`qoder`（plans 1 条）、`codebuddy`（plans 1 条）、`deepseek`（api 1 条）、`openai`（api 2 条）。
- **决定**：不为它们新建 `/vendor/<slug>/` 路线。
- **理由**：① 站上所有 `/vendor/<slug>/` 都以 **A 空间厂商名**为身份键生成；为这 5 家建页要么得为它们**新编 A 空间身份**（等于"因为套餐里有这个平台，就认定它是一家有 deals 的厂商"），要么得改掉这个身份键（结构性改动，会牵连已有 9 条 URL）；② 这些平台的资料本来就有正确去处：`/plans/coding/`、`/plans/api/`、`/plans/` 枢纽与各枢纽页。
- **结果**：`/vendor/` 页面集合与基点保持 **9 条不变**；题面 §4「Provider Page 至少包含 Deal / Coding Plan / API Pricing / Model 其中至少一种真实资料」由现有 9 页 + t8 新增区块满足，不靠"多建页"。
- **落点**：已写进 `docs/v3.0/AGENT-REFERENCE.md` §2.4 门槛表；`t8` / `t12` 以它为准。t3 这边的实测名单就是上面那 5 家（`report:coverage` 的「缺口 2：有 Plans 无 Deals 的 provider」正是同一个集合，可复算）。

### 6.3 数据齐备必须先于页面生成（硬顺序）

`report:coverage` 在 t6 落盘前后给出的数字不同：落盘前 Coding 是 provider 8 / plan 9、API 是 records 7 / items 37；
