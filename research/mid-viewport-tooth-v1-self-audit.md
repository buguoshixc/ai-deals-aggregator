对本轮[报告](research/mid-viewport-tooth-v1-report.md)的独立怀疑清单（`mid-viewport-tooth-v1-report.md`）。**我不是本轮的实现者**（本轮不改判据），
所以这里审的是「实验设计本身能不能被推翻」。

## 1. 结论先摆出来（哪一条硬、哪一条软）

| 结论 | 硬度 |
|---|---|
| V1（`761–1439px` 窗口）让 `§22c @950 逐条页面级说明` 变红，且是**唯一**变红的断言 | **硬**：883/1，四次运行的断言明细 + sha256 全在 `readings.json` |
| 旧三档（1440/1600/390）与样本两档（760/360）**逐字未变** ⇒ 950 是这一形态的唯一防线 | **硬**：`name::detail` 全串相等（`==` 比较，不是肉眼） |
| 只落在 `761–940` 的同一形态**四档全绿** | **硬**：883/0；探针显示规则在 900/940 生效、950 失效 |
| 950 档真正新激活的是 `@media (max-width:1180px)` | 中：基于「9 条 `@media` 条件 × 3 个视口」的枚举 + 首页 `.grid` 只读读数 |
| 「950 档覆盖 761–1439」**不成立** | 中偏硬：`[761,940]` 已实测；`[941,949]` / `[951,1439]` 只做了端点推理，**未逐段实测** |

## 2. 一个怀疑者会怎么打这个实验（逐条已挡 / 未挡）

1. **「你注入的规则真在 950 生效吗？」** —— 已挡：`probe.cjs` 完全**不经过** `verify-site.js` 的判据代码，
   只读 `getComputedStyle().maxWidth` 与 `clientWidth`。950 是 `452px`，1440/1600 是 `none`。
2. **「是不是 `narrow-unregistered` 先红、把 950 的窄列判据顶了？」** —— 已挡：断言 detail 里
   `未登记的窄阅读列 0 页`；注入刻意用 **px** 而不是 ch，正是为了**孤立** `narrow-unregistered`
   （那条码是视口无关的静态扫描，用 ch 会在 1440 也红，「只有 950 看得见」就没有判别力）。
3. **「是不是注入污染了页面结构，红的原因不是窄列？」** —— 已挡：注入是**追加在既有 `<style>…</style>` 内部**，
   不新增元素；`藏字 0 · 裁切 0 · 首屏说明过长 0 · note-unrendered 0`；`逐条判 271 条` 与基线一模一样。
   变红的只有「窄」这一族的三个码（`note-narrow` / `note-ink-narrow` / `note-axis`）。
4. **「883/1 里的那个 1 是不是本来就红？」** —— 已挡：同一副本、同一命令，基线 R0 = **883/0**。
5. **「还原是不是假装还原（从备份拷回来当然一样）？」** —— 已挡：还原用 `restore.cjs`，是 `inject.cjs` 的
   **逐字节逆运算**（在同一批文件上删掉注入的那一行，带「注入串必须恰好出现一次」的反空洞守卫）。
   还原后全树 sha256 回到 `67d1d0bd…337d`，残留注入串 **0**。
6. **「你为了凑红改了判据 / 阈值吧？」** —— 已挡：`git diff origin/master -- scripts dist docs NEXT-STEPS.md package.json` **为空**；
   断言总数四次都是 **883**（未增未减）。
7. **「V2 那条为什么不用一个能变红的注入来满足任务描述？」** —— **故意不这么做**：任务描述写的「761–940」与
   档位量测的宽度（950）在算术上不相交。把窗口悄悄换成 `761–1439` 只报「红了」而不说这件事，
   就是**把「判据没红」和「判据没覆盖」混为一谈**。所以两者都跑、都报。
8. **「950 档变红了，那它是不是已经把盲区堵死了？」** —— **没堵死，报告 §4/§9 明写**：950 是**单点采样**。
   同一形态只要把窗口改成 `(min-width:761px) and (max-width:949px)`，就又能四档全绿 —— 这一点**没有**用
   实测否定（`max-width:949px` 那一轮没跑），是**按算术推理**得出的；这是本轮**未实测**的残余面。

## 3. 未覆盖 / 不可外推（与报告 §9 同口径，不重复数字）

- 只测了「窄阅读列」一类形态；竖排 / 竖直裁切 / `note-unrendered` / `narrow-unregistered` 在 **950 档**
  没有各自的变异读数。
- 950 是点采样 ⇒「区间覆盖」不成立，且**已用 V2 证伪一半**（`[761,940]`），另一半是推理。
- 只有 Windows + msedge 一个引擎；CI 的 Ubuntu + chromium 未验。
- 耗时读数被本机多会话负载污染（同相位 11.0–21.4s），**只作了「同量级」的弱结论**。
- `.arch-v1/` 的注入产物与探针脚本不入库 ⇒ 报告里的数字**只能靠重跑复现**，仓库里可逐字节复核的只有
   `readings.json`（四次 `--json` 的断言明细原文 + 三份探针文本 + 五份全树 sha256）。

## 4. 该不该算 blocker？

**不算。** 判据本身没有问题：950 档对**它该管的形态**（生效于 950px 的缺陷）确实会响，读数硬。
需要改的是**表述**：上一轮报告与任务描述里「950 档覆盖 761–1439 盲区」应改写为
「950 档把盲区从『761–1439 无采样』缩小为『950px 这一个点被采样』」。这正是报告 §8 给 captain 的收口文字。
