# v2.0 前置审计：当前仍然纯人工的维护成本（Top N）

> 目的：在写任何 AI 代码之前，先用**可复核的数字**回答「人工成本花在哪」。
> 本文件里的每个数字都来自 2026-10-01 在 `master @ 2204565` 上的实测，命令与出处随文给出。
> 结论驱动下一节的落点优先级；**不先做这一步就选能力，等于按感觉接模型**。

## 二、Top N（按「当前真实成本 × 发生频率」排序）

### 1. 新来源上线 —— 小时级，且几乎全是逆向工程

**为什么贵**：一条来源要同时改四处，且每处都有自己的守卫。

| 位置 | 人工要做的事 | 守卫 |
|---|---|---|
| `scripts/collectors/*.js` | 读页面、试选择器、处理分页/无头 | `collectors/index.js` 的规矩：**只注册实测有产出的来源**（零产出不上线）→ 必须真跑通才算数 |
| `scripts/lib/provenance.js` `SOURCE_TYPES` | 登记新 source 名与档位 | `validate --strict` 的守卫：记录里的 `source` 在表里找不到就红 |
| `assets/logos/manifest.json` | 补厂商 logo | README 明写：manifest **由人维护**，`gen-manifest.js` 只做并集、永不覆盖 |
| `scripts/data/aliases.json` | 补标题别名（否则同一产品分裂成两条） | `dedup` 只看这张表 |

**最贵的一步是第一步**：今天没有任何页面结构证据留档（见第 2 条），
所以「选择器为什么没匹配上」只能靠人工重新抓取 + 二分。

### 2. 源失效 / DOM 改版诊断 —— 单次 30 分钟，且系统几乎不提供证据

**今天系统给诊断的东西只有这些**（`scripts/lib/health.js`）：

```text
status ∈ healthy|degraded|failed
reason ∈ collector_error | headless_unavailable | zero_output | zero_output_baseline | sharp_drop
lastError            —— 错误首行，截到 200 字
lastItemCount / previousItemCount / delta / consecutiveFailures / consecutiveZero
```

**系统不给的东西**（全仓搜索确认：`scripts/` 下不存在任何页面结构或选择器快照）：

- 上一轮页面长什么样、这一轮变成什么样；
- 采集器依赖的选择器/正则在当前页面上各命中几次；
- 是改版、跳登录、403、还是渲染方式从 SSR 变成 SPA。

于是维护者必须：重新抓页 → 读 HTML → 猜哪一层变了 → 改选择器 → 再跑一轮。
这就是本版本要把它从「30 分钟」压到「5 分钟」的那一条。

### 3. 六字段人工判断 —— 每条 10 个槽位，且「写错」与「没写」必须分开

一条记录的六字段有 **10 个槽位**：`audience(1) + benefitType(1) + eligibilityDetail(4) + claimRequirements(3) + availability(1)`。

专门为此存在的模块与证据：

- `scripts/lib/audience-audit.js` 整个文件只解决一件事：**人手写错枚举会被静默丢掉，表现与「本来就没写」完全一样**；
- 三态必须是字面量 `"unknown"`，`null`/`0`/`"true"` 都是非法（`audience.js:54` 的注释解释了为什么）；
- `basis:'inferred'` 必须配 `note`（≤200 字）——**推理链本身是断言的一部分**（`schema.js:841`）；
- `scripts/data/audience-overrides.json` 已经有 **56 条人工手写**，每条还带一段 `evidence` 推理串。

这段工作最适合 AI 出草稿：**有原文可引、有固定枚举、有确定性校验器兜底**。
风险也最集中：AI 最容易在「原文没写」的地方给出确定值 —— 这正是评测里要重罚的 `falseCertainty`。

### 4. 首次策展一条优惠 —— 15–30 分钟

除上面 10 个槽位，还要填 `discountInfo(≤240) / description(≤200) / eligibility(≤120) / validity(≤60) /
category(枚举) / pricingModel(枚举) / features(≤3 条 × ≤20 字) / priceLine(≤60) / expiresAt / verifiedAt`，
并且要守 `docs/DESIGN-RULES.md` 第 8 节与 `provenance.STAMP_PATTERNS` 的诚实性红线
（不许写「已核验」「100% 有效」「永久有效」）。

### 5. 疑似重复排查 —— 目前**没有**系统性手段

去重是精确匹配：`aliasKey(normalizeTitle(title))`（`scripts/lib/dedup.js:31`），
噪声词与别名表（`scripts/data/aliases.json`）全靠人手维护。
`validate.js` 里唯一的疑似重复检查是同区域内「一条标题是另一条的前缀」，而且只是 `warn`。

**漏掉的是哪一类**：跨语言 / 跨标题写法但同一个优惠，例如

```text
Cursor Student   /   Cursor Education Plan   /   Cursor 学生优惠
```

归一化之后三者互不相等、也不互为前缀 ⇒ 今天**完全不可见**，只能靠人眼扫全库（134 条、上限 300 条）。

### 6. 翻译 —— 3–8 分钟/字段，且上游一改写就重开

已有很好的作者循环（`zh-todo.js` 清单 → 填 → `--scaffold` 盖指纹），
门禁按指纹判漂移、按 7 天宽限判待译。当前待译 0，但 63 个字段的存量意味着
**每次上游大改都要重走一遍**。这一项 AI 只该出草稿，落地必须人工点。

### 7. `evidence` 引文回访 —— 134 条里只有 3 条

引文有全库预算（12000 字 / deals.json 的 5%），当前用掉不足 1%。
缺的不是预算，是**回访官方页并把原话摘出来**这件人工活。

### 8. Source Health 诊断工具的纯手工使用

`scripts/tools/inspect-source.js`、`scripts/tools/probe-sources.js`、
`.github/workflows/probe-sources.yml` 都需要人手动跑、人眼看输出。
它本身没错，但输出没有结构，没法与「上一轮」对比。

## 三、据此确定的 AI 落点（与实施顺序）

| 优先级 | 能力 | 直接对应上面第几条 | 为什么排这个位置 |
|---|---|---|---|
| A（地基） | provider 抽象 / 结构化输出 / 候选信封 / 缓存 / 成本 / prompt 版本 | — | 没有它，后面每加一个能力都要复制一遍调用与记账 |
| B1 | 优惠字段提取候选（带逐字段 evidence） | 3、4、7 | 频次最高、枚举最确定、有确定性校验器 |
| C | DOM Drift 诊断（结构摘要对比） | 2、8 | 单次成本最高，且系统今天**零证据** |
| B2 | 疑似重复候选 | 5 | 收益最直接（今天完全不可见），且结构上禁止自动合并 |
| B3 | 翻译草稿 | 6 | 已有成熟人工循环，AI 只补草稿 |
| E | 评测集与指标 | 全部 | 没有数字就没有「降低维护成本」的证据 |
| D | fixtures + collector patch 候选 | 1 | 唯一会碰采集器代码的能力，放最后、只出 diff |

## 四、本次明确不指望 AI 解决的

- **新来源的第一版 collector 本体**：仍然人工。AI 只在「已经坏了」时给诊断与候选补丁。
- **判断一条优惠「是真的」**：这是人的责任，AI 只提供候选与出处。
- **决定活动是否结束**：`expiry.js` 的确定性判据继续是唯一裁判。
