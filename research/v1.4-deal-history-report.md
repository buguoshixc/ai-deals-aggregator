## 二、六个问题的答案（机制）

| 问题 | 谁回答 | 说明 |
|---|---|---|
| ① 首次发现 | `created` 事件的 `at` | 存量记录**没有** `created` —— 只有一份标注「不是创建事件」的基线 |
| ② 免费额度何时改变 | `benefit_changed` | `discountInfo` / `pricingModel` / `priceLine` / `features` / `benefitType` |
| ③ 何时新增截止日期 | `expiry_changed`（`from === null`） | `expiresAt` / `validity`；由文案抽取得到的截止日标 `origin: derived` |
| ④ 领取条件何时变化 | `eligibility_changed` | `eligibility` / `eligibilityDetail` / `claimRequirements` / `audience` / `availability` |
| ⑤ 何时从官方页消失 | `ended` + `reason` | 两种含义分开说（见下） |
| ⑥ 是否消失后重现 | `ended` → `restored` 成对 | 记录被 prune 掉之后来源重新列出，也记 `restored`（历史是 `deals.json` 没有的记忆） |

**`ended` 的两种含义**（页面措辞分开）：

- `source_no_longer_lists`：来源**本轮健康且确实跑出条目**，但连续 `MISS_CONFIRM_RUNS = 2` 次没见到它
  （记录**仍在站内**）。页面说「来源不再列出（连续多次成功采集未见）」。
- `pruned_expired` / `pruned_overflow` / `retired_garbage` / `withdrawn`：记录**离开数据集**，
  原因直接取 `mergeAll` 手里的对象（不在历史层重写 prune 规则）。

**三道不误报的闸**：① 来源本轮失败 / 骤降 / 零产出 / 上一轮遗留 → 该来源不参与「未见」计数；
② `--only` / `--dry-run` / 被硬拦的运行完全不写历史；③ 人工策展条目不参与「未见」判定。

## 三、四方案比较（摘要，展开见契约第一节）

| 维度 | A 每日全量快照 | B git diff | C 显式事件 | **D 混合（选定）** |
|---|---|---|---|---|
| 仓库体积 | 236 KB × 2/天 ≈ **170 MB/年** | 0 | KB/年 | 同 C + 一次性基线 86.7 KB |
| Pages / 静态站 | 产物膨胀 | 运行时拿不到（需 `fetch-depth:0`） | 一个追加文件 | 同 C |
| 可重建性 | 事实全但语义读时推 | 派生自 VCS，规则改动被误当优惠变化 | 基线+事件可重放 | **重放 == 当前状态，机器可验** |
| 可信度 | 分不清「来源变」与「规则变」 | 提交时间 ≠ 观测时间 | 带 reason / origin | 最高（+ git 交叉校验） |

选 D 的关键取舍：**纯 C 没有锚点**，「日志与当前状态一致」无法验证，日志被手改不会有东西变红。
基线用**值**而不是摘要 —— 实测两者 JSON 体积几乎相同（key 脚手架占大头），而值基线还能人读、能审计。
`git diff` 的思路保留为 `npm run history:audit`（离线），**不进 CI**：浅克隆与历史重写都不适合当闸门。

## 八、诚实性与边界

1. 存量 134 条**没有**任何 `created` 事件：页面明说「变更记录自 2026-09-30 起（此前状态没有记录）」。
2. 没有事件时明说「暂无变更记录」＋「起算日之前的状态没有历史记录」——不用空白冒充「没有变化」。
3. 「不再收录」只说本站**未再观测到**，不说成厂商下架 / 优惠失效（块内固定免责句，构建与真浏览器各扫一遍）。
4. **人工策展条目没有自动的「来源消失」信号**：它们不经过采集器，生命周期事件只在记录离开数据集时产生（实际极少）。这是本阶段写下的边界，不是遗漏。
5. 观测态（`absence`）保留窗口 365 天：超出后若同一条再出现，会被记成 `created` 而不是 `restored`。
   事件日志里那次历史仍在，但自动识别「重现」的能力有窗口 —— 写在契约里。

## 九、遗留与技术债

1. **上限只红不缩**：事件数 / 文件体积触顶会让门禁红，压缩/折叠工具本阶段不做（保留最早 `at` 的折叠方案留作独立议题）。
2. **基线 86.7 KB 是一次性成本**，但它是单文件里最大的一块；将来若要瘦身，可改成只冻结「曾发生过变化的字段」（需要先有历史数据才能判断）。
3. **`history` 在 `dist/deals.json` 里是 per-deal 冗余**（与 v1.3 的 `sourceFacts` 同类取舍）：换来「浏览器只 fetch 一次、弹层与静态页同源」。
4. **`origin: derived` 只区分了两类规则推导**（`expiresAt` 抽取、`type` 重分类）。其余字段若将来出现规则性改写，需要在这里补登记。
5. **`--only` 子集运行不写历史**：这是刻意的（避免误报消失），但代价是「调试式采集」不会留下历史。

## 十、是否适合进入 `v1.5-change-radar`

**判断：适合进入。**

支持进入的证据：

- **数据层已就位且有牙**：`check:history` 强制「基线 + 事件重放 == 当前状态」，链断裂 / 静默消失 /
  未跟踪字段进日志全部会红；`history:audit` 提供第二把尺子。雷达（首页「最近变化」）需要的
  `事件 → 记录 → 页面` 三段都已经打通。
- **查询接口是纯函数、可直接复用**：`history.eventsFor/historyFor/summarize` 与 `historyOf()`（RENDER-CORE）
  已经是「按时间取变化」的形状；雷达只需要一个新的视图入口，不需要新的存储。
- **展示路径单一**：弹层与静态详情页共用 `detailHtml`，雷达若要做成静态页/入口行，可以沿用
  v1.2 的 `DIRECTORY_PAGES` 生成循环与 v1.3 的构建期派生模式（判据写一遍、结果进产物）。
- **体积余量充足**：事件当前 0 条、上限 20000 条 / 1 MiB，实测增长量级是 KB/年。

进入 v1.5 前必须先解决的两件事（v1.4 不代劳）：

1. **先有真实事件再设计雷达**：现在日志是空的。建议至少观察一个采集周期（2–3 天，
   CI 每天两次），确认事件频率与字段分布符合预期，再决定「雷达」按什么粒度聚合
   （按天？按记录？按事件类型？）——否则是在猜一个还没有样本的分布。
2. **首页密度是最贵的资源**：v1.2 的实测已经证明首屏卡片数是硬约束（入口行每多 30px 就少半张卡）。
   雷达的入口若放在首页，必须先量密度并接受取舍；另一条路是做 `/changes/` 静态页
   （可分享、无 JS 可读），与 `/need/` 同一形状 —— 成本更低、不碰首页。
