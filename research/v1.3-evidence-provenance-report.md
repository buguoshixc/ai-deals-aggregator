## 一、目标与结论

**目标**：让读者能自己判断一条优惠「从哪来、多久没被重新看到、最近一次成功采集在何时、
依据是什么」，且**不给站点自己盖章**。

**结论**：已完成。详情弹层与 80 个静态详情页出现统一的「信息来源」块，十行固定、缺值分清
`不适用 / 未知 / 不可用`；引文层有硬上限与全库预算；所有门禁实跑 0 失败。

## 二、六问的答案（摘要，展开见契约）

| # | 问题 | 结论 |
|---|---|---|
| 1 | provenance 数据模型 | **三层**：A 记录事实（已有字段，语义不变）＋ B 有界官方引文 `evidence[]`（新增，只人工写）＋ C 采集事实 `sourceFacts`（构建期派生，**只进 dist**） |
| 2 | 哪些字段已有 | `url` `sourceUrl` `source` `firstSeen` `lastSeen` `provenance{credibility,sourceUrl,verifiedAt,fields,contrib}` `verified/verifiedAt` ＋ `source-health.json` 的 `kind/lastSuccessAt/status` |
| 3 | 哪些可自动生成 | `firstSeen/lastSeen`（管线）、`provenance.*`（merge）、`sourceFacts{sourceId,method,lastSuccessAt,healthStatus,sourceType,lastSuccessState}`（构建期 join）。**引文与推理 `note` 永不自动生成** |
| 4 | 哪些不该长期保存 | 官方页全文/HTML/Markdown 快照、原始 HTTP 响应、截图、每条记录**每次运行**的尝试时间与瞬时错误、采集凭据、超过上限的引文 |
| 5 | 如何避免大规模复制 | 五条同时成立：条数 ≤3 · 单条 ≤200 字（**超长拒收，不截断**）· 全库 ≤12000 字且 ≤ deals.json 字节 5% · 出处禁聚合站 · 必须绑定一个 `field`。页面只展示片段＋出处链接＋采集日期 |
| 6 | 详情页如何展示 | RENDER-CORE 的 `sourceBlockHtml()`，弹层与静态页**同一个函数**：官方页面 / 原始出处 / 收录来源 / 来源类型 / 采集方式 / 首次收录 / 最近发现 / 最近成功采集 / 断言依据 / 官方原文片段 ＋ 固定免责句 |

### 关键取舍：为什么 `lastSuccessAt` 不写进源数据

它是**来源**的属性且每轮采集都刷新。写进 `deals.json` 会让 134 条记录天天全变一行 —— diff
失去意义，`check-reproducible` 的「重放产出同一份文件」也会退化成「前提是采集没发生」。
因此只在构建期做一次 join（`BUILD_ADDED = {collections, sourceFacts}`），机器可读的真值仍是
已发布的 `source-health.json`。

### 关键取舍：`known` 也是缺失状态之一

「最近成功采集」不是「有值 / 没值」两态，而是四态：

| 状态 | 页面措辞 | 含义 |
|---|---|---|
| `known` | `2026-09-30 01:48（北京时间）· 最近一次采集正常` | 有心跳且成功过 |
| `na` | **不适用** —— 本条来自人工策展，不经过采集器 | 按设计没有采集器 |
| `unknown` | **未知** —— 来源心跳里没有这一条 | 本该有、没匹配到 |
| `unavailable` | **不可用** —— 本次构建没有可用的来源心跳数据 | 构建期没有心跳文件 |

三种缺失的措辞互不相同由 `validate --strict` 强制（合成一句「暂无」会红）。

## 四、本轮暴露并修掉的三个真问题（都是实测，不是估算）

1. **`known` 被降级成「未知」（渲染层）**
   渲染层把 `lastSuccessState` 拿去 `SOURCE_STATE` 词表里查，而 `known` 不在那张表里
   （有值时显示的是时间本身）⇒ **每条真采到的记录都渲染成「未知」**，而当时构建自检全绿。
   修法：单独放行 `known`；并补断言「`known` 必须渲染出 `<time datetime>`」——
   没有这条断言，这个 bug 会一路发到线上。
   *发现方式：构建通过后**人工看渲染结果**，而不是靠门禁。*
2. **局部变量遮蔽模块（数据层）**
   `audience-overrides.applyOverride` 里原有一个局部 `provenance` 对象；v1.3 引入同名模块后
   `provenance.mergeEvidence(...)` 打到普通对象上，真实采集抛 `TypeError`（dry-run 抓到）。
   改名 `provenanceBlock`。
3. **心跳缺失的优先级（派生层）**
   `factsFor` 原先「先查行、查不到再看整份是否缺失」，于是调用方若同时传了心跳行与
   「文件缺失」标志，会渲染出一个**上一次的旧时间**。改为缺失标志优先。
   *发现方式：自测里那条「心跳整份缺失」用例当场变红。*

另外顺手收紧了两个静默风险：
- `audience-overrides-extract.js` 重新生成时会**原样带回**人工写的 `evidenceQuotes`
  （报告表里没有这一列，否则一次重建会静默删掉证据）；
- `check-reproducible.js` 新增「引文漂移」判据（引文是人工输入，必须原样穿过 merge；
  实测 0 处）。

### 上线后的线上实证（2026-09-30）与随之修掉的两个工具缺陷

PR #4 合并（`42d4fd9`）后 Deploy 工作流发布成功，线上实测：

- 线上 `deals.json`：`updatedAt=2026-09-30T09:36:21+08:00`、`count=134`、**带 `sourceFacts` 134 条**、
  **带 `evidence` 3 条**；
- 线上详情页（360智脑 / Anthropic 两条）：块 **10 行**、含「信息来源 / 最近成功采集 / 免责句」、
  人工策展显示「不适用」、引文渲染出来、**无「已核验」**；
- **线上整链路冒烟 `verify-site.js --url=`：256 项 0 失败。**

跑线上冒烟时暴露出两个**此前就存在**的工具缺陷（本地永远绿，因为本地服务在根路径）：

1. `verify-site.js` 里几处取样写死了 `/deals.json` / `/source-health.json`。线上是 GitHub
   **项目页**（挂在 `/ai-deals-aggregator/` 下），根路径 404 → 先报「取样前提」失败，
   接着 v1.3 的取样解引用 null **把整个套件崩掉**（前面 200 多项结果全丢）。
2. 「搜中国大陆」那条断言用固定 350ms 等防抖（前端防抖 120ms）。单跑这一段够用，
   整条套件跑到这里时实测出现过「350ms 后仍是未过滤的 50 张卡」的假红。

修法：地址一律由 `base` 解析（`new URL(..., base)`，本地根路径与线上子路径同时成立）；
取样失败**报一条失败**而不是崩溃；搜索改成等「卡片数真的变了」而不是赌固定毫秒
（判据没放松：等不到变化照样红，只是不再把慢当成坏）。修完线上与本地都是 256/0。

## 六、仍存在的问题 / 技术债

1. **引文覆盖率低（3/134）**：这是**正确结果**，不是缺陷 —— 引文只能人工写，本轮刻意没有
   自动回填。要提升只能人工逐条对照官方页（下一轮的编辑工作）。
2. **46 条记录没有 provenance**（旧条目）：页面如实显示「未声明依据」。补齐等于编造出处，
   留给人工来源逐步补。
3. **`sourceFacts` 是 per-deal 冗余**（同一来源重复 N 份）：约 20KB，只为换取「弹层与静态页
   共用同一个纯函数、且浏览器不需要第二次 fetch」。若将来条数规模显著上升，可改成
   `dist/source-index.json` + 运行时 join。
4. **`sourceType` 是声明表**，新增采集器必须登记，否则 `validate --strict` 红。
   这是**有意的**摩擦（静默显示「未知」更糟），但它确实是一处人工维护点。
5. `audience-overrides-extract.js` 的 `--check` 现在会因**键序差异**报「报告与数据没有互相
   印证」（v1.1 收口把键序规范化后的历史遗留）。它不在 CI 门禁里，本轮未动；下次要用它重建
   文件前需要先处理。

## 七、是否适合进入 `v1.4-deal-history`

**判断：适合进入，但 v1.4 的第一件事必须是「先定义历史存哪、多大、怎么裁剪」，而不是先写 UI。**

支持进入的证据：

- **事实层已就位**：`firstSeen`（单调变早，有断言）、`lastSeen`（取更晚）、
  `sourceFacts.lastSuccessAt`（来源级心跳）三者构成了「这条记录的时间轴」的骨架；
  v1.3 已把「时间」口径统一到北京时间并支持绝对时间渲染，历史视图可以直接复用。
- **可重建性有牙**：新增任何持久化结构都会被 `check-reproducible` 与
  `build selfCheck` 审到，不会出现「历史只存在于服务器某次运行的内存里」。
- **渲染路径单一**：弹层与静态页共用 `detailHtml` / `sourceBlockHtml`，历史块可以走同一条路，
  不必再造一份模板。

前置条件（v1.4 必须自己解决的，v1.3 不代劳）：

1. **新增一种持久层**：目前管线只保留「合并后的当前值」，没有逐次快照。
   历史需要 append-only 的变更日志（建议 `scripts/data/deal-history.json`，按 id 记录
   `{field, from, to, at}` 或更紧凑的补丁），并在 `mergeAll` 里由**一处**写入。
2. **体积与隐私边界**：必须定义保留窗口（如 90 天）与每条记录的变更上限，否则它会成为
   仓库里第一个无界增长的文件；同时明确「历史里只记字段变化，不记原文片段」。
3. **不能伪造历史**：现有 134 条**没有**历史数据。v1.4 的第一个可见状态是「从今天开始记录」，
   页面必须如实说明「历史从 YYYY-MM-DD 起」，不得拿 `firstSeen/lastSeen` 反推出一段假时间轴。
4. **门禁**：至少要有一条「历史是当前状态的函数」的可重建性判据 + 一条真浏览器断言
   （历史上确实显示变更、且空历史时明说「暂无变更记录」而不是空白）。

**结论**：v1.3 交付的是「客观事实 + 缺失语义」的地基，v1.4 是在这块地基上加一条**时间维度**；
两者没有设计冲突，但 v1.4 有明确的、必须新做的持久化设计（上面第 1 条），
不是「照现在的结构顺手加一页」。
