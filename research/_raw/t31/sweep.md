# t31 同类清扫：仓库里还有没有「用子串数字当精确条数」的断言

扫描方式（只读，全仓 `scripts/**/*.js`）：

```
grep -n "0 条|变更记录自"                                     # 全量人工过一遍
grep -nE "(includes|test|match)\([^)]*(待译|最老|不再收录|结束|恢复|条)[^)]*'"   # 数字 + 单位的子串/正则断言
grep -nE "/\\d\+ 条|/\\d 条|/\[0-9\]\+ 条"                    # 动态条数正则
```

## 汇总

- **真缺陷 1 处**（#1），已按同一修法处理：判据抽成 `lib/feeds.js` 的具名函数（数字边界）+ 页面验收改为调用它 + 自测夹具钉住。
- 其余 10 类全部**无风险**，理由如上（关键是看**数字两侧有没有锚点**：固定标签 / 空格 / 单位 / 括号）。
- 修完后全仓 `scripts/**` 里再没有「裸 `/0 条/` 判动态条数」的地方：`grep -n "/0 条/"` 只剩 **注释**（`lib/feeds.js` 的口径说明、`verify-site.js` 的解释注释、`feeds-selftest.js` 的小节说明与检查名），外加 `feeds-selftest.js` 里那条**故意复现旧写法**的回归钉（`ZERO_ENDING.every(text => /0 条/.test(text))`）——
  它断言的是**历史行为**（证明缺陷可复现），不参与任何生产判据，且与"页面验收必须调用具名判据"那条牙一起，保证裸子串不会再回到门禁里。
- 相邻类（不是本次范围，但记一笔）：`verify-site.js` 里有历史修复留下的注释，提醒「空集合上 `every()` 恒真」这一类陷阱；那类问题由各自的牙守着，且与"子串数字"不同源。
