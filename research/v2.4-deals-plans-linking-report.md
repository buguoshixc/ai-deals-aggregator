# Phase 2.4 Deals ↔ Plans 完成报告

> 范围：建立**优惠 ↔ 套餐的可校验双向关联**（关系模型 + Deal 页 / Plan 页 UI + 派生节省金额 +
> 候选报告 + 校验与门禁）。
> 真值文件：`scripts/data/deal-plan-links.json`。契约：`docs/SCHEMA-v2.4.md`。
> **`deals.json` / `plans.json` / `curated_plans.json` / 两份历史日志一个字节都没改。**

## 0. 开始前的核对（题面 §一）

| 要分析的东西 | 现场结论 | 对设计的影响 |
| --- | --- | --- |
| `deal.id` | `sha1(lower(vendor)\|lower(title)\|lower(url))[0..12]`（`lib/schema.js` 的 `makeId`） | 改标题 / 改 URL / 改厂商就换 id ⇒ **任何按标题推导关系的方案都会在改标题那一刻静默失效** |
| `plan.id` | `sha1(kind\|provider\|planNameKey\|period)[0..12]`（`lib/plan-schema.js` 的 `makePlanId`） | 与 deal.id 是两个不同底数的哈希空间，不能互推；period 进 id ⇒ 月付/年付本是两条 SKU |
| provider 归一 | deals 侧 `vendor` 是采集原文串（渲染期由 RENDER-CORE `vendorOf()` 归一）；plans 侧 `provider` 必须在 `providers.json` 登记（未登记硬红，精确别名匹配） | 「provider 一致」两半都要判（§5）；认不出原始串就必须写 `providerOverride` |
| `url` | deal.url 是官方（或聚合）入口页；plan.officialUrl 是定价页。两者常常不同页 | URL 只能当**候选**判据（同主机），不能当生产关系 |
| `title` | 采集标题里混着「免费/五折/学生」等营销词，且同一平台多个产品线共用品牌名 | 标题相似度只进候选报告（实测能产出「Google AI Pro → Cursor Pro」这类假阳性，正好说明它不能自动写关系） |
| current dedup | `lib/dedup.js` 的 `normalizeTitle/aliasKey` 做的是**采集去重**（别名表 + 噪声后缀） | 复用它做关联会把「同一家公司的两条不同产品线」并成一条，故不采用 |
| current schema | `validateDeal` 有字段白名单；`validatePlan` 会把归一器重跑结果逐字段比对 | 记录字段集**封闭**：关系只能放独立来源表（见 §1） |
| 数据现状 | deals 134 条 / plans 9 条；`expiresAt` **全为 null**；deal-history 与 plan-history 均 0 事件（仅基线） | 「已结束」不能只靠历史事件判，必须有由数据日期推导的判据（§4） |

**结论**：不做模糊标题匹配当生产关系；关系放**人工来源表**，视图走「派生字段只进 dist」的既有范式。

## 1. Relation Model（§二 / §三）

- 真值：`scripts/data/deal-plan-links.json` = `{ schemaVersion, links[], retired[] }`（`_note` / `_rules` 为说明键）。
- 一条 `links`：`dealId` · `planIds[]`（1–8，升序）· `provider` · `providerOverride`（可选）·
  `basis` · `evidence[]` · `confirmedAt` · `promo`（可选）。一条优惠一条记录，多个套餐写在 `planIds` 里。
- 一条 `retired`：`links` 的全部字段 + `title`/`vendor` 快照 + `endedAt` + `reason`
  （`campaign_ended` / `deal_pruned` / `plan_removed` / `relation_withdrawn`）。优惠记录被采集层下架后，
  关系仍以快照形式留在历史里（题面 §七）。
- 规范序：`dealId` 升序 → `planIds` 升序；记录内键序固定；重排 = 校验错误
  （与 `plans.json` 同一条纪律：输入顺序不影响序列化结果）。
- **派生值不落盘**：`savings` / `updatedAt` / `count` / `relatedPlans` 出现在源文件里就是错误。

**为什么不是记录内 `relatedPlanIds`**：两个数据集都是派生产物（`collect` / `plans:rebuild` 会重写），
字段集封闭（schema 白名单 + 归一器逐字段比对），手写字段会在下一次重建时**静默消失**；
而关系是人的显式断言，与 `providers.json` / `vendor-slugs.json` 同类，天然属于人工来源层。
放独立文件后 `check:reproducible` 与 `check:plans:reproducible` 完全不需要认识这一层（实测仍绿）。

**派生视图（只进 dist）**：`dist/deals.json` 每条有关系记录注入 `relatedPlans`
（`planId/title/regularText/regularCode/promoText/promoCode/periodText/quotaText/modelsText/promoLine/
eligible/savingsText/linkStatus/planStatus`），并发布 `dist/deal-plan-links.json`
（源表 + 派生 `updatedAt`/`count`，供外部核对）。源 `deals.json` 里出现 `relatedPlans` 会被产物自检报红。

## 2. Deal UI（§四）

`/deal/<id>/` 与首页详情弹层**共用** RENDER-CORE 的 `detailHtml()`（新增 `opts.prefix` 决定相对深度），
有关系时在「变更记录」之前插入 `.dplans` 块：

- 套餐名（链到 `/plans/coding/#plan-<id>`）；
- **正常价格 / 当前活动价 / 计费周期 / 额度 / 主要模型** —— 字段名与套餐对比表**逐字同名**，
  文字由 `plans-page.planRowOf()` 同一套格式化产出（不重写价格/额度口径）；
- `本优惠：<官方文案>[（限符合条件者）]`、`节省 ¥4.9/月`（可缺席）；
- 固定出口 `查看套餐对比 →`；
- 未知写「未标注」或表格里的「—」，不写 0、不留空；`linkStatus=ended` 显示「该优惠已结束」，
  `planStatus=removed` 显示「该套餐已不再收录」。
- **没有任何关系的优惠页一个字节都不多**（132 条里只有 3 条有关系；反向由产物自检钉住）。

示例（真实产物 dist 片段）：
`关联的正常套餐 · GitHub Pro · 正常价格 $10 USD · 当前活动价 — · 计费周期 每月 · 额度 1,500 积分 / 每月 · 主要模型 未标注 · 本优惠：已验证教师与热门开源仓库维护者可免费获得 Copilot Pro（资格限定）（限符合条件者） · 查看套餐对比 →`

## 3. Plan UI（§五）

`/plans/coding/` 表格之后、`#plans-compare` 之外新增 `#plan-deals` 块，**每条套餐各一行**：

- 有当前优惠：`当前优惠：<文案>[（限符合条件者）][ · 截止 <日期>]` + `节省 …`（可缺席）+ `查看优惠 →`（`../../deal/<id>/`）；
- 没有：`暂无当前优惠`（明确空态）；
- 有已结束 / 已退役：`历史优惠：<标题>（已结束 <日期>）`；记录已下架则不给链接（不留死链）；
- 块自带计数行（`共 N 条套餐 · 当前有优惠 M 条 · 历史关联 K 条 · 数据基准日 …`）与一条口径说明
  （「关联是显式确认的……相似度匹配只产出候选报告，不会自动写进这一页」）；
- 页面 `.stop` 汇总行加 `· 当前有优惠 N 条`；`PLANS_NOTES` 增两条（关系来源与「优惠结束后套餐不消失」）。
- **纯静态、零交互控件**（无 JS 也读得到，且没有「点了没反应」的东西）。

## 4. Current / Historical Relation（§七 / §八）

- `asOf = max(deals.json.updatedAt 的日期, plans.json.updatedAt 的日期)`，**不读墙上时钟**
  （同一天两次构建逐字节相同；跨零点也不会因为构建时刻而变）。
- deal 侧 `ended` 三种理由：记录不在 `deals.json`（`deal_pruned`）· 历史层最近生命周期为 `ended`
  （`deal_ended`）· `expiresAt < asOf`（`expired`）。plan 侧：不在表里 = `removed`；变化层 `ended` = `ended`。
- **`current` ⟺ deal 与 plan 都是 current**（`isCurrentRelation`，判据只有一处）。
- 优惠结束后：套餐行照旧在（套餐是长期 SKU），该行变「暂无当前优惠」，关系改记「历史优惠」；
  套餐被下线时关联仍保留（退役记录带快照，页面上不给死链）。

## 5. Savings Calculation（§六）

`savingsOf(plan, promo)` 四道门**缺一不可**，任一不满足返回 `null`（页面不显示这个字段，绝不写 0）：

1. `promo.appliesTo === 'all'`（资格限定的优惠对多数读者不成立 —— 教师/学生/受邀人三类种子关系因此
   **只显示优惠本身**，不显示「节省多少」）；
2. 同币种（`promo.currency === plan.billing.currency`）；
3. 同周期（`promo.period === plan.billing.period`）；
4. 正价与优惠价都是有限数、差额 > 0。

结果 `round((regular − price) × 100) / 100`，文本复用套餐表币种符号与千分位（`节省 ¥30.1/月`）。
「同套餐」由关系本身保证。题面例子（40 → 9.9）在自测里逐字覆盖：`节省 ¥30.1/月`。

**当前生产数据里没有一条「全员可享」的关联**（GitHub 教师/学生、MiniMax 受邀人都是资格限定），
所以线上暂时不会出现节省金额 —— 这是诚实的结果，而不是没实现：四道门的正/负样本都在自测里，
且用「去掉某一道门 → 断言变红」的方式实跑过（§9）。

## 7. Validation（§八）

判据只在 `lib/deal-plan-links.js` 一处，`validate.js` / 构建期 / 自测 / 真浏览器都从它取期望值。

- **硬错误**：形状 / schemaVersion / 未知字段 / 非规范序 / 重复 `dealId` / `planIds` 空或重复或非升序 ·
  dealId 或 planId **不存在** · `provider` 未登记 · 套餐 provider 与声明不一致 ·
  provider 不一致且无 override（**多余的 override 也报错**）· `promo` 形状非法 · 派生键手写 ·
  `basis` 非法 · 引文缺失/非法/非归一形态 · `retired` 快照缺失或与 `links` 重叠。
- **`--strict` 下升级为错误**：`links` 里的优惠已结束（报错信息直接给出可粘贴的 `retired` JSON 片段）、
  关联套餐已被变化层记为 ended。
- **警告**：`editorial-confirmed` 的条数（让「靠人判断」的部分一眼可见）。
- 接入：`npm run validate`（含 `--strict`）· `npm run build`（校验不过即中止）·
  `npm run verify`（读产物重算「哪些算当前」再与 DOM 逐条对账）· CI 门禁新增一步。

## 11. 已知限制

1. **节省金额线上暂不出现**：三条种子关系都是资格限定（教师/学生/受邀人），按 §5 第 1 道门不算节省。
   门本身有正负样本与牙齿测试，等出现「全员可享 + 官方给出可比价格」的关系时会自动生效。
2. **`links` 里出现已结束的优惠会让 `validate --strict` 变红**（这是故意的：要求人把它移进
   `retired[]`，错误信息给出可粘贴片段）。日常 `npm test`（非 strict）只给警告，不拦开发循环。
3. **套餐被移出 `plans.json` 后**，退役关系仍在文件里，但页面上不再有它的落点（不为它编链接）。
4. 关系是人工维护的：新增优惠与套餐不会自动建立关系，只会在候选报告里出现。
5. `promo.price` 允许是「由官方百分比推出的价格」（如 9 折 × ¥49 = ¥44.1），此时 `note` 必须写清
   推导过程（种子数据就是这么写的）；这一层不替人做这类算术。
6. 与并行会话的隔离措施：验证构建走 `--out=dist.v24`（已加入 `.gitignore`），
   `NEXT-STEPS.md` / `PROJECT_STATUS.md` 与两份数据文件**未被本阶段改动**；
   本阶段记录即本报告与 `docs/SCHEMA-v2.4.md`。

## 12. 是否适合进入 Phase 2.5
