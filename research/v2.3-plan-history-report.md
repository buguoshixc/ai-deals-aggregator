## 1. History Architecture（§一：哪些抽成通用框架、哪些不共享）

### 1.1 事实起点（先核对，再动手）

| 检查项 | 实际情况 |
|---|---|
| plans 有采集器吗 | **没有**。`plans.json` 是 `curated_plans.json` 经 `npm run plans:rebuild` 的**确定性产物**（离线、不联网、不读墙上时钟），且发布时与源逐字节相同 |
| 现有 history 是给谁的 | `lib/history.js` 是 deals 的日志：跟踪字段表、事件类型、`ended` 判据全部与采集器来源健康绑定（`source-health.json` / `CURATED_SOURCES`） |
| `changes.js`（变化雷达）能直接复用吗 | 不能直接复用分栏：deals 有「即将结束」（依赖 `expiresAt`），套餐没有绝对到期日；deals 还有一套「文案微调降级」，而 plans 的文案归一**前置**在差异计算里 —— 再实现一遍就是两套判据 |
| 现有两套日志的风险 | 复制一份 `history.js` 是最坏的写法：两份重放实现迟早在行为上分家，而分家之后**两边都还是绿的** |

### 1.2 抽象结论：机制共用一份，判据各写一份

新增 `scripts/lib/history-core.js`（**唯一**的机制实现），`history.js` 改为委托（公开 API 逐字不变）。

| 抽进内核（与业务无关） | 留给领域（**刻意不共享**） |
|---|---|
| 值归一 / 确定性序列化（`normValue` `stableJson` `sameValue`） | 事件类型表（deals 的 `benefit_changed` / `eligibility_changed` 在套餐里没有对应物） |
| 一次性基线 + 事件重放（`replay` / `applyFieldEvent`） | 跟踪字段表与中文措辞（同一件事两种说法） |
| 链校验 + 「基线+事件 ⇒ 当前状态」一致性（`verifyStore`）+ 上限 | 「消失」的判据（deals 靠来源健康；plans 没有采集器，见 §5） |
| 事件身份 `eventKey`、排序、观测态裁剪、有界渲染视图、统计 | 数组语义（deals 的 `features` 是整体；plans 的 `supportedModels` 按元素做集合差） |

内核为了容纳 plans 只加了三个**通用**扩展点（都不含任何一方的专有词汇）：
`profile.readField`（支持 `billing.regularPrice` 这样的路径）、`profile.compare`（按字段覆写相等判据）、
`profile.applyEvent` / `eventValueMatches`（元素级数组事件的重放与链校验）。
另外区分了 `recordKey`（数据记录上的键名 `id`）与 `eventKeyName`（事件上的键名 `planId`，按题面 §四 命名）。

**边界有牙**：`plan-history-selftest` §⑭ 静态扫描钉住三件事 —— 内核里不许出现任一方的专有字段 / 事件类型；
两个领域层里同名的机制函数必须是「转手调 `core.*`」的薄包装；`plans-selftest` §⑪ 复核边界
（deals 链路：采集 / 合并 / 历史 / 优惠雷达 / 落地页 / SEO **一个字都不提 plans**；订阅层是唯一一条
允许引用 plans 的通道，且不许自己读数据文件）。

## 2. Event Types（§二）

17 类 = 题面 11 类 + 6 类 schema 逼出来的：

| 类别 | 类型 |
|---|---|
| 生命周期 | `created` · `ended` · `restored` |
| 价格 | `price_changed` · `promo_started` · `promo_ended` · `promo_changed` · `billing_changed` |
| 额度 | `quota_increased` · `quota_decreased` · `quota_changed` |
| 模型 | `model_added` · `model_removed` · `model_changed` |
| 其它 | `restriction_changed` · `availability_changed` · `updated`（记录级元信息，低价值） |

新增的 6 类与理由（逐条登记在契约 §4）：`promo_changed`（活动价换挡，既不是开始也不是结束）、
`quota_changed`（口径/周期变化或数值 ↔ `null` —— 不能谎称增减）、`model_changed`（同名模型的
role/note 变了，不是增删）、`availability_changed`（题面 §三点名的 `availability` 在 plans 里由
`region` 承担）、`billing_changed`（币种变化）、`updated`（元信息，与 deals 的 `updated` 同名同义）。

**事件结构**：`{ planId, eventId, at, type, field, from, to, origin, runAt }`；生命周期事件不带
`field/from/to`；`created` 带 `fields` 快照与可选 `supersedes`；`ended` 带 `reason` 与可选
`firstMissedAt` / `label`（墓碑快照）。
对题面示例键名（`date` / `before` / `after`）是**有意偏差**并已登记：这里用 `at` / `from` / `to`，
与 v1.4 的优惠日志逐字一致 —— 两份日志共用同一个内核，键名不同会让每一处机制都要分叉。

## 3. Meaningful Fields（§三）

`meaningfulPlanFields`（13 个，顺序即序列化序）：`billing.regularPrice` · `billing.promoPrice` ·
`billing.currency` · `quota.type` · `quota.amount` · `quota.period` · `quota.description` ·
`supportedModels` · `restrictions` · `region` · `officialUrl` · `source` · `sourceUrl`。

**不重要的变化一个事件都不产生**（逐条理由在契约 §5.2）：`lastSeen`（人工每次回访都会刷新 ⇒ 记它等于
每轮造 9 条假事件）、`verifiedAt` / `verified`（核验是我们的动作）、`evidence`（抄写差异）、
`billing.note` / `billing.promoNote`（自由文本备注，题面 §三点名）、`derivedMetrics`（**派生值**：
输入变了自然有事件）、以及身份字段（`id` / `provider` / `planName` / `billing.period`）。

**`quota.description` 的投影**（这一条是本阶段最需要判断的设计）：它只在 `rate_limited` /
`unlimited_fair_use` / `other` 上是「被跟踪的额度口径」（这些类型的额度语义全在文字里）；
量化型（`tokens` / `credits` / …）的说明是解释性散文 ⇒ 投影为「不跟踪」。
**空白与标点**差异一律不产生事件（NFKC + 去空白类与标点类字符后比较），
但文字本身差一个语义就照样记（含数字、字母、`≥` / `+` / `%` 这类符号）—— 不做相似度比较。

## 4. Stable IDs（§五）

```
eventId = sha1(planId|type|field|at|from|to|reason|created?fields|ended?firstMissedAt|created?supersedes).slice(0,12)
```

- **派生字段**：`verifyStore` 重算并逐条比对，手写必红（与 `plan.id` / `derivedMetrics` 同一条纪律）。
- 「同一真实变化重复运行不重复产生事件」的保证有**两道**：链校验（重放出的当前值 == 事件的 `to` ⇒ 跳过）
  与 `seen` 集合按 `eventKey` 幂等。实测见 §9 牙 3 与 E2E 的「再跑一次追加 0 条」。
- `eventId` 同时是套餐变化订阅源的 `<guid>` —— 页面、日志、订阅源上「同一件事」只有一个身份。
- **时间单调性**：`at` 只来自数据（`plans.json` 的 `updatedAt`），且若早于该套餐上一条事件的日期，
  写入路径**拒绝写盘并报错**（不猜日期）—— 实测见 §9 补牙 A。

## 5. Ended Protection（§七）

plans 没有采集器，所以**没有复用** `source-health.json` 的连续失败计数（那是 deals 采集器的心跳）。
六条规则（契约 §8）：

| 规则 | 内容 |
|---|---|
| R1 唯一写入点 | 只有 `rebuild-plans.js` 成功写盘时写日志；来源层有硬问题或 `--dry-run` ⇒ 数据与日志都不动 |
| R2 缺席确认 | 连续 **2 次**成功运行未见才记 `ended(source_no_longer_lists)`；每次成功写盘都推进计数 |
| R3 批量熔断 | 单次缺席 `>= max(3, ⌈已知总数×0.5⌉)` 或输出为空 ⇒ 不推进、不记 `ended`，只留档 `anomalies[]`；确属真实批量下架须显式 `--allow-mass-removal`（记 `ended(withdrawn)`） |
| R4 周期重键 | 同一次运行里同 `(kind, provider, planNameKey)` 而 `billing.period` 不同 ⇒ **立即** `ended(period_changed)` + 新记录 `created(supersedes)` |
| R5 fail-closed | `plans.json` 缺失/损坏/校验失败 ⇒ 门禁红 + 拒绝写 |
| R6 已知限制 | 确认期两次 ⇒ 人工删除后存在「数据已无、日志未记」的窗口；由 notice 与「待确认」清单点名 |

**这六条要防的事**：deals 的形态是「采集器坏了 → 所有条目被标成消失」；plans 的形态是
「来源层被误清空 / 被批量删掉 → 所有套餐被标成下架」。上面的 R1（坏输入进不了写盘路径）
与 R3（批量熔断）正好分别挡住这两种。实测见 §9 的 D2b / D3 与 §10。

## 6. Change UI（§八 / §九 / §十）

三处展示，**措辞只有一处实现**（`plans-page.planChangeTextOf`），且全部是**构建期静态 HTML**：

| 位置 | 内容 |
|---|---|
| `/plans/coding/` 表格之前 | 「最近变化」块 `#plan-changes`：最近 5 条（`date + 平台 套餐 + 变化`），例如 「正常价格 ¥99 → ¥68」/「新增模型 DeepSeek V4.1」/「活动价开始：¥9.9」/「不再收录（人工来源层不再列出）」；末尾一行「变更记录自 {date} 起 · 全部变化 →」 |
| `/plans/coding/` 行内详情 | 「变更记录（N 条）」时间线：最近 10 条 + 「另有 N 条更早的记录未在此显示」；`updated` 类元信息**只在这里**出现 |
| `/changes/` | 顶部锚点导航「优惠变化 / 套餐变化」+ 表格后的「套餐变化」四栏（今日新增 / 最近 7 天变化 / 不再收录 / 重新出现，各 30 行上限）。**没有新做一页** |

两个刻意的取舍：

1. **块必须放在 `#plans-compare` 之外** —— 那个容器的 `innerHTML` 会被 `plans-compare.js` 整块替换，
   静态内容放进去等于被抹掉（无 JS 的读者会看到空块）。行锚点 `id="plan-<id>"` 加在数据行上，
   于是「最近变化」与订阅源都能深链到**那一行**。
2. **空态与不可用分开说**：日志可用但没有变化 → 「当前没有观测到套餐变化」；
   日志缺失/损坏 → 「本次构建没有拿到套餐变更日志…这不表示「没有变化」」。两句话在
   「最近变化」块、套餐时间线与 `/changes/` 分栏里保持一致。

## 7. Feed（§十一）

新增 `/feed/plans/coding/changes.xml|.json`（`kind: 'plan-changes'`，**与 deals 的两份变化源并排**，
不是它的变体）：

| 项 | 值 |
|---|---|
| `<guid isPermaLink="false">` | 日志里的派生 `eventId`（页面 / 日志 / 订阅源同一身份） |
| `<link>` | `…/plans/coding/#plan-<planId>`（套餐没有独立详情页，深链落到那一行） |
| 条目集合 | 套餐变化视图里**除记录级元信息外**的全部变化（窗口与页面同一份判据） |
| 空 Feed | 允许为空（`mayBeEmpty`）：空是事实（起算日之前没有可观测的变化） |
| 对账 | `feeds.validate()` 新增分支：guid ↔ 重算事件身份、链接页面存在、元信息不进订阅；构建期另断言**每条深链的锚点在页面上真的有落点** |

规模变化：Feed **23 → 24**（文件 46 → 48）· `/feeds/` 页新增「套餐」分组并把空态单独说 ·
订阅发现 **120 → 124** 条 `rel="alternate"`（套餐对比页与 `/changes/` 各多声明一对）。

**上线后打线上 Feed 抓到的一处真实文案 bug（同日修复）**：套餐变化源的空态**复用了优惠那一句**
（`FEEDS_NOTES.emptyChanges`），于是订阅源对着读者说

> 自起算日起，还没有观测到**优惠内容、领取条件或有效期**的变化。

而套餐根本没有「领取条件 / 有效期」这两个面 —— 读者会以为这份订阅漏了优惠。
修法：新增 `FEEDS_NOTES.emptyPlanChanges`（「自起算日起，还没有观测到套餐的价格、活动价、额度、模型、
限制或销售地区的变化。」），套餐变化源只用它；并**加一条牙**（`selftest:feeds` §九）：
套餐的空态必须提到套餐的变化面，且**不许**出现「优惠内容 / 领取条件 / 有效期」—— 复用 deals 的句子会当场红
（`selftest:feeds` 83 → **84**）。教训与本仓既有的那条一致：**同一句话在两处复用时要先问它说的是不是同一件事**；
这次是「上线后打线上产物」而不是「本地看构建日志」发现的。

## 11. 已知限制

1. **`ended` 要两次确认**（R2）⇒ 人工删掉一条套餐后，`plans.json` 立刻不再包含它，而日志要到
   **下一次**成功重建才记 `ended`。这个中间态是合法的（`verifyStore` 放行），但必须有人知道：
   `rebuild-plans.js`、`check:plan-history`、`report:plan-changes` 三处都会点名「待确认」。
2. **周期重键有个时序边界**：`ended(period_changed)+created(supersedes)` 只在「旧记录与新记录
   出现在同一次运行」时成立。若旧记录先消失、新记录下一次运行才出现，则走常规的两次确认路径，
   那时 `supersedes` 无从建立 —— 如实记成两条独立的变化，**不猜**。
3. **没有模型注册表**（v2.1 的既有边界）：模型改名会产生 `model_removed` + `model_added` 一对事件。
   这是「以厂商原文为准」的代价，不是 bug；Phase 2.5 若建注册表，这一层的 alias 归一才有落点。
4. **量化型套餐的 `quota.description` 不跟踪**：厂商用文字改口径（例如换算公式的措辞）而数值与类型
   都没变时，本层不产生事件。这是题面 §三的直接要求；`rate_limited` / `unlimited_fair_use` / `other`
   三类不受影响（它们说明**就是**额度语义）。
5. **没有自动发现能力**：套餐没有采集器，本层记录的是「人工核对官方页后改了什么」，不是
   「厂商官网今天改了什么」。这一点与 v2.1 的定位一致，也是 Phase 2.4/2.5 之前不会变的前提。
6. **页面载荷没有扩到历史**：套餐对比页的交互载荷（筛选/排序用的机器键）**没有**加入历史字段 ——
   历史只出现在静态块与详情模板里。理由是 9 条时载荷 5 KB 无所谓，但按套餐线性加事件会让
   页面体积不可控（v2.2 报告点名过这件事）；真要按需取，应当另做设计而不是默认线性增长。

## 12. 是否适合进入 Phase 2.4

**适合。**

**判断依据**

1. **数据侧闭合**：`plans.json` 一个字节没改（可重建门禁原样通过），历史层是**另一份** append-only
   文件，且「基线 + 事件重放 == 当前数据」这条一致性是可机器验证的（新门禁步骤）。
2. **机制不再有分家的可能**：内核只有一份实现，两条边界（内核不含任一方专有词汇、deals 链路不提 plans）
   都有静态扫描的牙。
3. **退出保护有实测**：R1–R4 在真实写盘路径上跑过四个端到端演示（改价 / 批量删 / 单条删两次确认 /
   坏输入拒绝写盘），不是只跑了单元夹具。
4. **三处展示与订阅都接了同一份判据**：页面块、时间线、`/changes/` 分栏、订阅源的条目集合都来自
   `buildPlanRadar` 与同一个句子函数，构建期与真浏览器各对账一遍。

**进入 2.4（Deals ↔ Plans 双向关联）时应当先想清楚的三件事**

1. **关联的锚点用 id 还是身份键**：`deal.id` 是 `sha1(vendor|title|url)`，`plan.id` 是
   `sha1(kind|provider|planNameKey|period)`；两者都会因改名/换 URL **换 id**。关联表若写死 id，
   一次改名就会让关系静默失效 —— 建议显式关系表 + 校验（题面 §八 已要求），并让 `check` 在
   「关联的一端不存在」时变红，而不是让页面少显示一块。
2. **provider 与 vendor 是两套身份空间**（v2.1 §9 的 C7）：关联必须显式对照或写明 override，
   不能拿字符串相似度当生产关系。
3. **`ended` 的语义在两边的差别**：deals 的 `ended` 是「来源不再列出」，plans 的 `ended` 是
   「人工来源层不再列出」。2.4 的「当前优惠」判定必须读**各自日志**的生命周期，不能拿一个开关糊两边。
