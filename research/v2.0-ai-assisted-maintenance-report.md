## 一、AI 使用边界

你给的红线逐条落成了**可执行的断言**，而不是文档里的承诺：

| 红线 | 怎么保证（可复核） |
|---|---|
| 不绕过 validate 写 `deals.json` | 全仓只有 `scripts/tools/ai-apply.js` 会写生产数据，它写的是两个**已有人工来源层**；`deals.json` 由 `mergeAll` 重新推导 |
| 不直接删除生产优惠 | AI 层没有任何删除路径；`ai-apply` 只有字段写入分支 |
| 不把 `unknown` 填成确定值 | 候选层规则 R1：非 `unknown` 的断言没有**同名逐字引文**即判 `invalid`（牙测试 1） |
| 不直接决定活动结束 | AI 输出里**根本没有**「已结束」这个结论位；`lib/expiry.js` 仍是唯一裁判 |
| 不自动合并疑似重复 | `scripts/ai/dedup.js` **不导出**任何 merge/apply/write 符号（牙测试 4，符号表断言） |
| 不自动改 collector 并推 master | `ai/patch.js` 只返回 diff 文本；仓库里**不存在**自动应用工具；`ai-maintenance.yml` 无 commit/push（CI 断言 16） |
| 不生成「官方没写」的优惠事实 | 提示词 + 候选规则 + 评测头条指标 `falseCertaintyRate` 三处一起管 |
| AI 不进采集链路 | `collect.js / store.js / dedup.js` 源码里不得出现 `scripts/ai`（牙测试 5 静态断言） |

## 二、Candidate 架构

统一信封（`scripts/ai/candidates.js`），每个候选至少可回答「谁、何时、基于什么」：

```json
{ "candidateVersion": 1, "id": "0128f15964cc", "task": "extract_offer", "dealId": "a67c07bf4993",
  "sourceUrl": "…", "generatedAt": "…", "provider": "openai-compat", "model": "…",
  "promptVersion": "extract-offer-v1", "inputHash": "sha256:…",
  "candidate": { "audience": ["student", "developer"], "…": "…" },
  "evidence": [ { "field": "audience", "quote": "Students and developers can claim the free credits", "sourceUrl": "…" } ],
  "confidence": { "audience": 0.9 },
  "status": "candidate | invalid | needs_human | accepted | rejected",
  "deterministic": { "schema": "pass", "enum": "pass", "evidence": "pass", "audienceAudit": "n/a" },
  "review": { "decision": null, "at": null, "note": null } }
```

- `confidence` **只是 AI 自己的置信度**，不参与任何取值仲裁，只用于审阅排序。
- `status` 是**候选**的状态；deal 记录本身没有 `status` 字段（没有新增任何字段，契约不变）。
- 不合格的候选进不了列表，落 `.ai-cache/invalid/<task>.jsonl` 供回看模型到底吐了什么。

## 三、Provider 抽象

`scripts/ai/provider.js` 的 `generateStructured()` 是 **AI 的唯一出口**；采集器永远不直接调模型。

```js
{ ok, result|null, invalid: { reason, detail, rawExcerpt }|null,
  meta: { task, provider, model, promptVersion, inputHash, cacheKey, cached,
          generatedAt, durationMs, usage: { inputTokens, outputTokens, estimatedCostUsd, costKnown } } }
```

- **永不 throw**：所有失败收敛成结构化 invalid（reason 闭集 11 个：`json_parse / schema_invalid /
  enum_invalid / missing_required / too_large / timeout / http / no_provider / budget_exceeded /
  mock_missing / provider_error`）。
- 四个 provider：`openai-compat`（换厂商只改 `AI_BASE_URL`/`AI_MODEL`）、`anthropic`、
  `mock`（回放，CI 与评测用）、`fail`（故障注入，**只给牙测试用**），外加 `off` 状态。
- 只用 Node 内置 `fetch` + `AbortController`，**没有新增任何依赖**。

## 四、Structured Output

- `scripts/ai/schemas.js`：6 个任务的 JSON Schema，**枚举全部从生产单一出处派生**
  （`AUDIENCES / BENEFIT_TYPES / ELIGIBILITY_KEYS / CLAIM_KEYS / CATEGORIES / EVIDENCE_LANGS`）。
  生产枚举变了，AI 侧自动跟着变，不存在「两处各写一份」。
- `scripts/ai/json-schema.js`：零依赖的受限校验器（`type/properties/required/additionalProperties/
  items/minItems/maxItems/minProperties/enum/const/oneOf/minLength/maxLength/minimum/maximum`）。
  写了不支持的词（`$ref`/`format`/`allOf`…）会被判**编写错误**（fail-closed），而不是静默忽略。
- `json_parse / schema_invalid / enum_invalid / missing_required` ⇒ 候选无效，**不做自动修复**。
  唯一的宽容是剥掉一层 Markdown 代码围栏（传输层包装，不是语义修复），且会记在 `meta.jsonSalvage` 里。

## 五、Evidence 要求

- **R1**：任何非 `unknown`/非空的受管字段，必须有一条 `evidence[].field` **同名**且 `quote` 非空的引文，
  否则 `invalid(evidence_missing)`。
- **R2**：三态只认 `true | false | "unknown"`；`null` / `0` / 字符串 `"true"` 一律无效（牙测试 2b/2c）。
- **R3**：枚举必须来自生产单一出处。 **R4**：`confidence ∈ [0,1]`。
- **R5**：候选引文 ≤7 条（每个可断言字段一条）、每条 ≤200 字。
  **与生产侧的 3 条刻意不同**：那是版权预算（存进 `deals.json` 的总量受全库上限约束），
  候选侧要的是证据覆盖；两者混用会让「断言了 4 个字段」的候选永远带不满证据、只能被判无效。
- **`needs_human`**：有引文但**没有否定线索**的 `false` 断言（如「注册后即可使用」撑不起「不需要信用卡」）
  不判无效，而是降级进审阅表的「无据的确定」单列，接受它必须显式 `--allow-unsupported` 并写依据。

## 六、Offer Extraction

- 入口 `npm run ai:extract -- --limit=10`；输入 = 官方页正文（净化后 ≤12000 字）+ 页面 metadata +
  我们当前的提取结果（**标为"仅供定位，不是证据"**）。
- 两种输入来源：`--source=fetch`（真抓官方页，维护时用）与 `--source=record`（只用记录自身文本，离线可复现）。
- 实测规模：**134 个单元**，每个约 1.3 KB 输入。
- 提示词里最硬的一条是「**不要用你的先验知识补**」——模型知道 Cursor 有学生优惠，那是噪声，
  我们要的是「这一页今天写了什么」。`unknown` 在这里不是失败，是正确答案。

## 七、Duplicate Detection

- 先跑**确定性预筛**（同 host / 同 `aliasKey` / 标题包含 / 字符二元组相似度 / 同厂商，加权后 ≥0.25），
  把 134 条的两两组合 **8911 对压到 60 对**（默认上限）再送给模型。
- 输出严格按你给的五分类：`same_offer / same_product_different_offer / same_vendor / unrelated / uncertain`。
- 审阅表把 `same_vendor` **单独成组**并标注「同厂商不等于同一优惠」；`ai-apply` 对重复候选**一律拒绝**，
  唯一的合并路径是人工改 `scripts/data/aliases.json`。
- 现状实测：全库 134 条里 `aliasKey` 重复组 **0 组** —— 也就是说，这一能力今天**没有真重复可抓**，
  它的价值是防患于未然，以及防止「同厂商被误判成同一优惠」。

## 八、Translation Assistant

- 入口 `npm run ai:translate`，输出 `scripts/data/translations_zh.candidates.json`（我们自己的英文，可入仓），
  **绝不写** `translations_zh.json`。
- 「哪些字段还要译」**不另写判据**：直接调 `zh.normalizeZh()`（它已经处理原文指纹与失效停用）。
- `scripts/ai/translate-guard.js` 是确定性守卫，先过关才允许被人接受：
  数字集合（允许月名展开与 `70% off → 3 折` 的合法换算）、币种、URL/域名逐字保留、厂商专名保留、
  否定语气双向、`trial` 不许变「免费」、`credits` 不许变现金、没有长期表述时不许出现「长期有效/永久」、
  `up to` 不许被抹平、没有日期时不许冒出年份。
- 落地 `npm run zh:apply-candidates -- --id=…`：用**当前**英文重跑守卫（防上游改写后草稿过期）+ 译文门禁，
  红了回滚。
- 现状：**0 个待译单元**（63 个可译字段已全部有人工译文）—— 能力在，但今天没活可干。

## 九、DOM Drift Diagnosis

- **捕获零改动采集器**：`lib/http.js` 与 `lib/browser.js` 是仅有的两个网络/内容出口，
  摘要只挂这两个出口（各约 6 行）。没有开启捕获作用域时是空操作。
- 摘要内容（`scripts/lib/dom-digest.js`）：标记（login/captcha/cloudflare/errorPage/consentOnly/spaShell）、
  计数（table/tr/td/card/li/heading/link/form/script/div）、形态（hasDataTable/hasCards/scriptToTextRatio）、
  `textLength`、**我们自己在 `scripts/data/source-probes.json` 里声明的**探针命中次数（selector/regex/关键词）、
  class 名直方图。**没有标题文本、没有正文。**
- 体积实测（真抓 Layer3Labs）：原始页面 **50,814 字节 → 摘要 1,388 字节（2.7%）**。
- 跨运行两代快照 `scripts/data/source-snapshots.json`，随数据入库（不入库就永远只有"这一次"）。
- 诊断 `npm run ai:diagnose`：输入两代摘要 + 差异 + 探针声明 + 采集器源码（**我们自己的代码**）+
  健康状态与 `lastError`；输出固定 enum 的候选原因 + 必须引用具体数字的依据 + 探针修改建议。
  **永不改采集器。** 当前命中 2 个来源（两个无头源 stale/lastRunMissing）。

## 十、Collector Patch Candidate

- `npm run ai:patch -- --source=<采集器 id>`：输入 = 诊断候选 + 采集器源码 + fixture。
- **自证**（这是这一条唯一值得说的部分）：`applyUnifiedDiff()` 是一个最小 diff 应用器（上下文逐字校验），
  把补丁应用到临时副本（`.ai-cache/patch-scratch/`，`lib/`、`data/` 用 junction 指回仓库），
  真的 require 进来跑一遍 fixture，把「能不能应用」与「会不会回归」变成数字：

  ```text
  好补丁    → 补丁可应用=pass · fixture 回归=pass（13 → 13 条）
  破坏性补丁 → 补丁造成 fixture 回归：期望 13 条，实际 0 条   → 候选判无效
  越界补丁   → 拒绝：只允许改 scripts/collectors/**
  ```

- **仓库里没有自动应用工具**：人 review 之后自己 `git apply`。这从结构上杜绝「AI 修 collector → 自动 push」。

## 十一、Fixtures

- 4 份，共约 **15 KB**：`layer3labs.deals`（7,442 B / 13 条）、`cn_qianfan.deals`（1,875 B / 17 条）、
  `futuretools.list`（4,857 B / 6 条）、`futurepedia.list`（1,176 B / 3 条）。
- 每份 = `page.min.html`（**最小的真实 DOM 片段**，自动最小化只留 `class`/`href` 等解析器真正读的属性）
  + `expected.json` + `PROVENANCE.md`（出处 URL、抓取日期、保留了哪块 DOM、裁掉了什么、版权说明、怎么重建）。
- `expected.json` 是**生产解析器在这个片段上的真实输出**，并且重建时会**断言它与整页输出在同一批条目上一致**
  —— 于是 fixture 证明的是「解析器在这个片段上仍给出同样的结果」，而不是「我手抄了一遍当前行为」。
- `npm run fixture:test` 离线回放（**已进门禁**）。为此把 4 个采集器的 `parse()` 与抓取分离（行为不变）。

## 十二、Cache

- `.ai-cache/`（**整个目录 gitignore**，含第三方网页正文，按版权纪律不入仓）。
- key = `sha256(task | promptVersion | provider | model | inputHash)`，**不含时间戳、不含随机数**
  —— 同一份输入在任何机器上算同一个 key（自检里断言了「与时间无关」且「随 promptVersion/model 变化」）。
- 损坏的缓存当未命中，并把损坏事实报给调用方。
- **不变量**：`collect / merge / build` 一律不读 `.ai-cache/`，所以缓存丢了不影响任何生产数据
  （`check-reproducible` 的两条定点判据因此不受影响）。

## 十六、Evaluation Result

**先说结论里最要紧的一句：本机没有 API key，所以前两臂不是模型分数。**
`research/v2.0-ai-eval.json` 的 `limitations` 里逐条写明了这一点（18 条）。

| 臂 | 测的什么 | 结果 | 能不能当模型分数 |
|---|---|---|---|
| 1 字段提取 | mock 录制响应 6 条 / 42 个叶子 | precision 0.667 · recall 0.190 · **falseCertaintyRate 0.1667** · unknownAccuracy 0.833 · 无据断言 4 条被规则拦下 · 非法枚举 1 条被 schema 拦下 | **不能** —— 测的是工装 |
| 2 疑似重复 | mock 录制响应 4/30 对 | 准确率 0.25 · **`same_vendor → same_offer` 危险错误 2 对** · 现有确定性去重会合并 0 对 | **不能** —— 同上 |
| 3 译文守卫 | **不调模型**，真测量 | 63 篇人工译文 **误报 0**；10 条篡改 **检出 10/10（1.0）** | **能** |

臂 2 有一处必须说清楚：金标 30 对**全部**是 `same_vendor`（预筛排序把中文模型条目排在了前面），
所以「准确率」这个总数几乎不携带信息，有意义的是**危险错误计数**与混淆矩阵。
这是数据分布的真实情况，不是评测写坏了 —— 报告里如实记，并留了后续动作（见第二十二节）。

臂 3 的价值在于它**抓到了两个真洞**，而且都已修复并复测：

```text
m01 删掉译文里的一个数字   → 曾经漏检（守卫对 "N%" 的豁免写得太宽，译文把 70% 整个删掉也放行）
                             → 修成「只有真的换出了折数才允许百分比数字消失」→ 现在检出
m06 英文删掉否定、译文仍有「无需」 → 曾经漏检（只查了 en→zh 一个方向）
                             → 新增 negation_invented（只认「无需/不必/未要求」这类强否定结论，
                               刻意不认裸的「不」——那会把正确译文大批判红，规则就会被关掉）→ 现在检出
```

修完之后，**63 篇人工译文的误报仍然是 0**（这条回归比检出率更重要：会误报的守卫等于没有守卫）。

## 十九、AI 故障时的降级行为

| 故障 | 行为 | 实测 |

| 单条超时 / 非 2xx / 非法 JSON | 该条记 `invalid` 并继续 | ✅ 牙测试 5 |

## 二十一、哪些能力仍需人工确认

**本轮默认：零自动接受。** 每一项产出都需要人点过头才会落地：

| 能力 | 必须人工做的部分 | 为什么不能自动 |
|---|---|---|
| 字段提取 | 逐条点 `ai:accept`（无据的还要 `--allow-unsupported` + 写依据） | 「引文是否真的支持这个结论」是语义问题，正则判不了 |
| 疑似重复 | 判断 + 人工改 `aliases.json` | 合并是破坏性操作，错一次静默删一条真优惠且 `provenance` 永不回春 |
| 翻译 | 逐条点接受 | 力度放大读起来更顺，人眼最难发现 |
| DOM 诊断 | 判断原因是否成立、自己改采集器 | 诊断错会让人去改本来没坏的地方 |
| 补丁候选 | review diff，自己 `git apply` | 改采集器 = 改数据来源 |
| 数据质量审计 | 把发现**收敛成确定性规则**或写明不收敛的理由 | AI 判断不能作为长期门禁（见下） |

## 二十二、后续自动化建议

按「可以开始讨论自动接受」的门槛（连续评测稳定 + 明确 evidence + 已有确定性 validator）排序：

1. **先补真实评测**：有 `AI_API_KEY` 后跑 `AI_EVAL_LIVE=1 npm run ai:eval`，把真实精度填进报告。
   在此之前，任何「自动接受」都无从谈起。
2. **把 dedup 金标补平衡**：当前 30 对全是 `same_vendor`（预筛排序所致）。下一步按**信号类型分层取样**
   （同 host / 标题包含 / 高相似度 / 纯同厂商各若干），否则「准确率」这个数没有信息量。
   注意：全库目前 `aliasKey` 重复组为 0，**没有真重复可标**，所以只能靠构造的近义对。
3. **审计发现 → 确定性测试**（这一版最重要的设计原则）：`ai/audit.js` 要求模型给出
   `suggestedValidatorRule`，本轮的 14 条可疑记录与它们的触发信号（`absolute_claim_unsupported` 10 条、
   `eligibility_text_student_unsupported` 8 条、`number_not_in_evidence` 1 条）应当逐条判定
   「变成 `validate.js` 的断言」还是「不收敛并写明理由」。收敛之后 AI 只需要处理**新形态**。
4. **最可能先达到自动接受门槛的字段**：`benefitType`（枚举确定、有明确词典）与 `audience`，
   条件是 ① 真实评测里的 `falseCertaintyRate` 足够低、② 落地前仍有 `audience-audit` 与 `validate --strict` 兜底、
   ③ 只对**策展来源**自动（采集来源的身份变更仍人工）。
5. **`ai-maintenance.yml` 可以加定时**（例如每周一次 `diagnose`），但**必须保持只出 artifact**：
   一旦它开始提交，`check-ci-consistency` 的 (16) 会红 —— 那是有意的。

## 最后：AI 现在具体帮维护者节省了哪些工作？

不写"接入了某某模型 API"，只写**哪一步不用人做了**：

### 1. 一个来源坏了：从 9 步降到 5 步，其中 4 步是"人肉找证据"

| 改前 | 改后 |
|---|---|
| ① 看到 Summary 说某源 0 条 | ① 同一处 |
| ② 手跑 `inspect-source.js` / `probe-sources.yml` | — |
| ③ 重新抓页 | — |
| ④ 肉眼读 HTML 找哪一层变了 | ② `npm run ai:diagnose`（自动带上两代结构摘要差、探针命中、采集器源码） |
| ⑤ 二分试选择器 | ③ 读候选原因（**每条依据都必须引用具体数字**，如 `td: 80 → 0`） |
| ⑥ 改代码 | ④ 改代码 |
| ⑦ 重跑采集看有没有数据 | ⑤ `npm run fixture:test` 立刻判回归 |
| ⑧ 没恢复 → 回到 ③ | ⑥ 重跑采集确认 |
| ⑨ （无判据，只能靠"看起来好了"） | — |

**省掉的是 ②③④⑤**：重新抓页、肉眼读 HTML、二分试错、以及"改了但不知道有没有改坏"的盲跑。
证据从"一行 200 字的错误"变成"昨天 `td=80`、今天 `td=0`，且 `markers.login=true`"。

### 2. 人工新增/修正一条优惠：从"手填 10 个槽位"变成"审一份带引文的候选"

一条记录的六字段有 **10 个槽位**（audience 1 + benefitType 1 + eligibilityDetail 4 + claimRequirements 3 +
availability 1），外加内容字段。今天 `scripts/data/audience-overrides.json` 里**56 条是人手写的**，
每条还配一段推理链。AI 现在把这一步变成「看候选表 → 点接受」，
而且**没有引文的断言根本进不了这张表** —— 省掉的主要不是打字，是"翻官方页找那句话"。

### 3. 疑似重复：从"全库人眼排查"变成"只看候选列表"

134 条两两组合 8911 对，现在是**一张按危险性排序的候选表**（`same_vendor` 单独成组并标注
「同厂商不等于同一优惠」），而且**结构上无法自动合并** —— 要看的那几对一眼就能看完。

### 4. 一条真实事故被这次评测提前抓掉了

译文守卫的两个洞（百分比豁免过宽、凭空加否定）**在人工使用中几乎不可能被发现**：
前者只在"数字真的被删掉"时沉默，后者只在"英文删了否定、中文还留着"时沉默。
10 条程序化篡改把它们变成了可复现的红。**这一条不是"省时间"，是"原来根本不会发现"。**

### 5. 还没有省掉的（如实说）

- **新来源的第一版 collector** 仍然要人工写（AI 只在"已经坏了"时给诊断与候选补丁）；
- **判断一条优惠"是真的"** 仍然是人的责任；
- **翻译**当前没有活可干（63 个字段已全部人工译好），这一能力是给下一次上游改写准备的；
- **真实模型精度未知**（本机没有 API key），所以"AI 判得准不准"这个问题**还没有答案**，
  报告里给的是评测工装与守卫的实测，不是一个漂亮的准确率数字。
