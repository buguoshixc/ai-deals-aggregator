## Feed 架构

### 先审当前 Feed：五个必须修的问题

v1.0–v1.5 只有一份 `renderFeeds()`（`build-local.js:475-523`），产出 `feed.xml` + `feed.json` 各 80 条。逐项核查结果：

| # | 问题 | 证据 | 处置 |
|---|---|---|---|
| 1 | **主链接全部导出站外**：`<link>` 与 JSON `url` 都是厂商官方页 | `:487`、`:514` | 主链接改本站 `/deal/<id>/`；官方页进正文 + JSON `external_url` |
| 2 | **条目时间不是事件时间**：`pubDate` = `lastSeen` | `:489` | 改 `firstSeen`（首次发现，永不漂移） |
| 3 | `lastSeen` 每轮采集都刷新（策展条目刷成今天），日期整体漂移 | v1.4 `UNTRACKED_FIELDS` 早已写明 | 只作正文事实行；机器可读时间字段改由事件决定 |
| 4 | 排序键 `lastSeen` 无二级 tie-break | `:474` | 显式全序（§Stable ID） |
| 5 | 构建期只查「两份 feed 条目数是否相等」，**没有任何结构/语义校验** | `:2821-2839` | 换成 `feeds.validate()`（20 个检查码） |

顺带修掉三处既有缺口：JSON Feed 缺 `date_published`/`icon`/`favicon`；RSS 缺 `atom:link rel=self`/`<image>`/`<category>`；`/changes/` 声明的是全量 Feed（v1.5 报告 §九-5 自记的技术债）。

### 三层结构

```
deals.json ─┐
            ├─ audience.js 的谓词 ──→ A 类优惠 Feed（当前有哪些符合这个条件的优惠）
deal-history.json ─┐
                   ├─ changes.buildRadar() ──→ B 类变化 Feed（最近发生了什么）
                   └─ 详情页的「变更记录」
```

- `scripts/lib/feeds.js` 是这一层的**唯一权威**：注册表 + 纯函数条目构建 + 两种序列化 + XML 良构检查器 + `validate()`。
- 构建期只算一次雷达，首页条带、`/changes/` 页面、变化 Feed 读的是**同一份结果**。
- 构建产物：`feed.xml`、`feed.json`、`feed/**`（36 个文件）、`icon.png`、`feeds/index.html`。

### 判据的复用（不是复刻）

分类 Feed **指向既有页面注册表**（`COLLECTION_PAGES` / `NEED_PAGES`），用它们的 `title`/`label`、`description`、谓词函数：

```js
{ id: 'china', pageKind: 'need', pageSlug: 'china-usable' }
```

于是「Feed 里的条目集合」与「页面表格里的行」被**同一个函数**锁在一起，构建自检再逐条 id 双向对账。订阅层没有新写一条判据（自测有一条静态扫描盯着）。

## 优惠 Feed 与变化 Feed 的区别

| | A 类：优惠 Feed | B 类：变化 Feed |
|---|---|---|
| 回答 | 当前有哪些符合这个条件的优惠 | 最近发生了什么 |
| 条目 | `deals.json` 的当前记录 | 雷达分栏（`created` / 高价值字段变化 / `ended` / `restored`） |
| 身份 | `deal.id` | 事件身份的哈希 |
| 时间 | `firstSeen` / 最近一次高价值变化 | 事件日期 |
| 变化时重推 | **不会**（id 与时间都不随采集刷新） | 会（新事件 = 新条目） |
| 空 | 不正常（分类 Feed 为空即构建红） | 正常（起算日之前没有可观测的变化） |

两类**不混**：优惠 Feed 不夹带事件，变化 Feed 不夹带「当前全部优惠」。
`new` 是 `changes` 的子集，这一点写在契约与 `/feeds/` 页面上。

**文案微调与元信息永不进 Feed**：变化 Feed 的条目直接取雷达的分栏结果，
`description` 改一个标点、`category`/`region` 这类记录级改动走的是雷达的 `other` 两个桶，
根本不进订阅 —— 与 v1.5 同一条红线。

## Stable ID 方案

| 类别 | `guid` / `id` | 依据 |
|---|---|---|
| 优惠条目 | **`deal.id`**（12 位十六进制，与 v1.0 起逐字相同） | `id = sha1(vendor\|title\|url)`，由 v1.1 的 schema 保证稳定 |
| 变化条目 | `chg:` + `sha1(history.eventKey(event))` 前 16 位 | 直接复用 `record()` 已有的幂等去重身份，不新造 |

三条决定各有理由：

1. **优惠条目刻意不加前缀**。现状就是 `deal.id`；改成 `deal:<id>` 会让所有老订阅者在升级那一刻**重收 80 条**。保持原样 ⇒ v1.6 升级零重复推送。
2. **变化条目刻意不用可读 id**。`chg:<dealId>:<at>:<type>:<field>` 读起来友好，但采集每天跑两次，**同一天同一字段可能连续变化两次**（`A→B`、`B→C`），可读形式会碰撞。`eventKey` 含 `from`/`to`，不会 —— 自测里有这条夹具。
3. **`eventKey` 不含 `runAt`**，所以构建/运行时间不可能影响身份（自测直接断言）。

优惠 id 与变化 id 命名空间不相交（12 位十六进制 vs `chg:` 前缀）。同一 `deal.id` 出现在多份优惠 Feed 里是正确的（每个 Feed 是独立订阅），「id 唯一」的口径是**每份 Feed 内唯一**。

## 防重复机制

四个层次，逐层都有机器守卫：

1. **身份只由数据决定**：优惠用 `deal.id`，变化用事件哈希；`runAt` 不参与。
2. **时间只来自数据日期**：
   - `pubDate` / `date_published` = `firstSeen` 或事件 `at`；
   - `date_modified` = 最近一次**高价值事件**的日期，没有就**省略字段**（不拿每轮刷新的 `lastSeen` 顶替）；
   - `<lastBuildDate>` = `deals.json` 的 `updatedAt`（数据时间，不是构建时刻）。
3. **产物里没有时钟**：`feeds-selftest` 对 `lib/feeds.js` 做静态扫描（剥掉注释后）禁止 `Date.now` / 无参 `new Date(` / `process.env` / 网络调用 / 写盘；`check-feeds-reproducible.js` 在真实产物上核对「所有时间字段都是北京时间零点」。
4. **序列化顺序确定**：全序排序 + `JSON.stringify` 依固定键序，输入键序不影响输出。

**实测量化**：连续 10 次真实构建，36 个 Feed 文件逐字节一致（指纹 `b0170cd284ba`）。

## `/feeds/` 页面

`/feeds/` 是订阅中心（构建期静态生成，零 JS）：

- 开头一句实话：「本站没有账号、没有邮件列表、没有推送服务，也不会记录谁订阅了哪一份 —— 它们就是静态文件」。
- 分组列出全部 18 个 Feed：**全部与变化**（3）· **学生**（2）· **开发者**（4）· **厂商订阅**（9），每行给出标题、描述、条数、最近一条日期、**RSS 与 JSON Feed 两个可复制的绝对地址**，以及到对应页面的链接。
- 变化流为空时**如实解释**：「本站的变更记录自 2026-09-30 起算，此前没有历史。空订阅是**事实**，不是故障」。
- 满足站点既有的五条约定：自指 canonical · 声明根订阅源 · 两段 JSON-LD（`CollectionPage` + `BreadcrumbList`）· 进 sitemap（`priority 0.6`，低于详情页 0.7 —— 它是给想订阅的人的入口，不是找优惠的入口）· 预渲染 2958 字（无 JS 可读）。
- 页脚新增入口「优惠变化：变化雷达 · **订阅这些优惠**」，与既有那一行**合并**，不增加页脚行数（避免 5 种输出全部变高）。

- **首页 `<head>` 只暴露四个订阅选择 × 两种格式 = 8 条** `rel="alternate"`：全部优惠 · 最近变化 · 学生优惠 · 开发者优惠。

| # | 篡改 | 结果 |

| **T1** | 同一 Feed 里两个条目用同一个 `guid` | `guid-unique` 红 ✅ |
| **T2** | student Feed 混入 `audience` 不含 student 的条目 | `predicate-holds` 红 ✅ |

| **T4** | Feed 链接改成不存在的站内 URL | `link-exists` 红 ✅ |
| **T5** | 连续构建 10 次 | 36 个文件逐字节一致，id 不变 ✅ |

T1–T4 在 `feeds-selftest` 里对**真实构建结果的深拷贝**做定向篡改，断言 `validate()` **恰好**报出对应 code（且未篡改副本 0 problem —— 防止验证器退化成永远红的噪声）。两个实现细节值得记下来：

- 篡改条目后必须**重新序列化**，否则验证器先报「三方对账不一致」——那是序列化没跟上，不是要验的那条语义；
- JSON 深拷贝会丢掉 spec 上的**判据函数**，必须接回去，否则 T2 会因为「没有判据可查」而**静默通过**（最危险的一种假绿）。

T5 分两层：自测内在内存里跑 10 次纯函数；`check-feeds-reproducible.js` 跑 **真实完整构建**。

**另外做了一次真实链路投毒**（验证「构建必红」的接线，不只是验证器本身）：临时在 `lib/feeds.js` 里让 `feed.xml` 的第 2 条复用第 1 条的 id、并把第 1 条链接改成不存在的页面，然后跑 `npm run build`：

## 仍存在的问题

1. **变化订阅交付当天是空的**。`deal-history.json` 起算日就是 2026-09-30、事件 0 条，「最近变化」与「最近新增」两份 Feed 都是 0 条。页面与 Feed 的 `description` 都如实说明这是**事实**而不是故障，但「订了暂时没内容」这件事只能靠时间解决。建议至少观察一个采集周期（2–3 天，CI 每天两次）再来评价变化流的分栏与窗口。
2. **厂商 Feed 的 URL 稳定性只兜住一半**。`≥3 事件` 那一支是永久兜底，但「曾 ≥2 条、现跌到 1 条且事件 <3 条」的厂商会失去订阅地址。做粘性注册表需要新增一份持久状态文件，本轮刻意不加 —— 这个缺口写在这里，而不是留给以后猜。
3. **`ai-coding` 只有 4 条**，因为判据只能按 `category` 收（数据模型里没有「是否用于写代码」这个字段）。缺口在页面与报告里都写明了：补法是给采集侧加字段，不是放宽判据。
4. **`expiresAt` 覆盖 0/80**，所以「即将结束」类订阅暂时不提供。等覆盖率上来再谈（现在做只会得到一个永远空的 Feed）。
5. **CI 多跑一次完整构建**（`Feeds reproducibility` 步骤），门禁时间约 +1 次 build。
6. **首页 `rel="alternate"` 从 2 条增到 8 条**，Feed 的 `<title>` 从站点名改为 `AI Deals Radar · <具体分类>` —— 老订阅者的**根 Feed URL 与 guid 不变**（零重推），但条目正文与 feed 标题会变，阅读器里会看到一次「订阅被重命名」。品牌串集中在 `FEED_BRAND` 一处，想改回中文站名只改一行。
7. **`icon.png` 是本轮唯一新增的二进制产物**（144×144，RSS `<image>` 规范上限）。它是现场用零依赖 PNG 编码器画的，规格合规但不是设计师作品。
8. **`/feed/`（文件，单数）与 `/feeds/`（页面，复数）不同名** —— 按需求指定，但这确实是后来人容易混淆的一处。

## 下一阶段建议

**先解决第 1 条：拿到真实变化样本。** 本轮把订阅的「取视图 → 序列化 → 验证 → 门禁」整条链子铺好了，但变化流的价值完全取决于事件的数量与质量。建议：

1. 让采集链跑满 3 天（约 6 次采集），观察 `deal-history.json` 的事件类型分布；
2. 用 `npm run report:feeds` 与 `npm run report:changes` 复核「哪些变化进了订阅、哪些被降级为文案微调」；
3. 如果出现误报（把不重要的事推给读者）或漏报（重要变化没进），**先改 v1.5 的高价值判据，而不是在订阅层加过滤** —— 订阅层只搬运雷达的判断。

**之后可以做的（按价值排序）**：给 `/feed/vendor/*` 补一个「该厂商的变化」维度（事件样本足够后再设计）；把 `/feeds/` 做成可按标签组合的少量「意图 × 格式」矩阵；把 Feed 的 `title`/`description` 做一次多语言化（现在只有中文，而 `language: zh-CN` 是实话）。

**关于 `v1.7-seo-expansion`：适合进入。** 三条理由：

1. **本轮刚好把 SEO/GEO 的地基补齐了**：主链接回归站内（此前 80 条条目全部把权重导出站外）、`/feeds/` 成为新的可索引入口并进 sitemap、`atom:link rel=self` 与 `icon`/`favicon` 齐备、`/changes/` 有了自指的订阅出口。
2. **可发现性有一条现成的待办**：`research/GAP-MATRIX.md` 的 G1（路径型条目页数量）在 v1.0 补了 80 个详情页，但结构化数据与内链深度还有空间；v1.6 新增的 36 个 Feed 文件也是可被索引的静态资源。
3. **门禁是够用的**：`verify:regress` 的密度基线、`check:ci` 的 workflow 冻结、以及本轮新增的订阅三层验证，都会在 SEO 改动里第一时间变红 —— 也就是说 v1.7 有安全网，不会「改完没人发现坏了」。

**唯一的前置条件**：变化订阅拿到真实样本之前，不要动 `changes.js` 的判据（窗口、高价值定义），否则订阅会跟着抖 —— 而「订阅抖」在读者端表现为重复推送，正是这一阶段花最大力气防的那件事。
